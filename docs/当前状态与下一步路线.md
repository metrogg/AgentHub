# 当前状态与下一步路线

最后更新：2026-06-04

这份文档是 AgentHub 当前的“事实总览”。它的目的不是讲历史，而是让开发者和 AI Agent 先对齐现在到底在做什么、什么已经定了、什么还在推进。

## 当前一句话定位

AgentHub 当前运行时主路径是 IM 式多 Coding Agent 协作，产品北极星是 `Coze 风格的开源 AI 工作平台`。

用户在群聊里提出目标，Manager / Orchestrator 像团队负责人一样理解意图，决定回复、追问、补员、组队、派活或总结；多个 Coding Agent 在真实子对话里执行，主群聊展示 Manager 的计划、进度、成员回报、产物和最终汇总。后续会在这条主路径之上继续长出 Space、Task Center、Asset Center、Expert Center 和 Eval / Trace。

底层重构方向已经进一步收敛为 AgentHub Product Shell + HiClaw-lite Open Kernel：前端继续保留 AgentHub 自己的 Coze / Kimi 风格操作界面，底层协作内核学习 HiClaw，并优先采用成熟开源组件。通信层采用真实 Matrix homeserver（优先 Tuwunel，兼容 Synapse/Conduit），不是本地表模拟；Manager Runtime 学 OpenClaw / QwenPaw；Worker Runtime 继续强化 Claude Code / OpenCode / Codex / Gemini，并可补充 OpenClaw / QwenPaw Worker；共享存储采用 MinIO/S3-compatible 语义，任务契约和产物以 `shared/tasks/{taskId}/...` object refs 为主，本地 filesystem 只作为开发 fallback 和项目镜像；AI Gateway 抽象化，短期可接 LiteLLM，长期目标 Higress；A2A 暂不作为内部主通信路径，只保留为外部互操作或 Matrix event 中的可选任务语义 envelope。后续要逐步把 `Room`、`Run`、`Task`、`WorkerInstance`、`Artifact`、`RuntimeLease`、`TimelineEvent` 做成一等资源。

最新的 HiClaw wiki 深读结论已经同步到 `docs/HiClaw架构调研与AgentHub底层重构方案.md`：我们要学的是 Manager-Workers 协作范式、Room 作为真实通信资源、shared task directory 作为任务协作空间、Worker 作为可协调资源、Human-in-the-Loop 作为一等参与者，以及 Gateway/consumer 风格的凭证隔离。后续可以直接参考 [hiclaw-wiki.agent.final.md](./hiclaw-wiki.agent.final.md) 和本地 [../hiclaw源码参考/](../hiclaw源码参考/)；不要把它简化成“做几个子对话”或“加一个任务看板”。

当前仍处开发阶段，旧会话、旧任务、旧数据库和旧 workspace/storage 数据不再是架构约束。旧数据能低成本只读展示就展示，不能展示可以清除重建；不允许为了旧数据保留旧流程、旧入口或旧 schema。

## 当前权威边界

- **Agent Runtime / Agent Base**：架构口径从 `Coding Tools` 收敛为 Agent 基座。OpenClaw / QwenPaw 优先作为 Manager / Team Leader 基座；Claude Code / OpenCode / Codex / Gemini 是主要 Worker 基座。`llm` 不再作为产品主路径 Agent runtime，只保留非核心 fallback。
- **通信协议**：Matrix 是内部协作事实源；A2A 是外部互操作协议，不是 runtimeType。
- **前端事件**：AG-UI 是运行事件到前端状态的唯一收敛方向。
- **协作契约**：Spec / Contract 只描述范围、产物、验收和路径边界，不做固定模板或静态路由。
- **执行隔离**：迁移期仍有项目工作区 + `.agenthub/workdirs` + 兼容旧 `.agenthub/handoff` + local sandbox root；新内核方向是 Worker workdirs + RuntimeLease + MinIO/S3-compatible ArtifactStore / SharedStorage，不把 Git 分支隔离当默认事实。
- **固定模板**：不再恢复经典团队模板、自动 Researcher/QA 注入、关键词路由、静态兜底提示词。

## 当前主路径

```text
用户在群聊发消息
  -> messages.ts 作为 ChatIngress 写入消息并加载群聊上下文
  -> OpenClaw/QwenPaw Manager Runtime 通过 SOUL/skills 判断下一步：回复、追问、补员、派活或总结
  -> 简单聊天：Manager / Orchestrator 直接回复
  -> 能力不足：Manager / Orchestrator 输出结构化 memberProposals，用户在主群聊卡片确认后才创建/加入真实 Agent
  -> 复杂任务：Manager-first planning action 生成团队行动方案和任务看板
  -> Manager skills 调用 Controller API 创建 run/task/task room/worker lease
  -> 每个任务创建真实 TaskThread / Matrix task room / RuntimeLease
  -> WorkerRuntime 从 Matrix task room 接单
  -> Codex / Claude Code / OpenCode / Gemini / OpenClaw Worker 执行
  -> 过程写回 Matrix Room timeline，任务契约和产物登记到 MinIO/S3-compatible SharedStorage / ArtifactStore
  -> Room timeline / RunEvent / ArtifactStore 投影前端看板和子对话状态
  -> ManagerLoop 基于 Run/Task/TaskThread/Room timeline/ArtifactStore 做最终复盘并完成 run
```

## 现在已经明确的方向

1. 群聊主线是核心产品，不做固定模板壳。
2. 多 Agent 协作必须是真执行，不是 Orchestrator 假装多人。
3. AgentHub 的中期产品目标要对标 Coze，不再只当作“多 Agent 聊天工具”。
4. Contract 要做成质量门和产物链。
5. 运行过程要事件化，前端要完全收敛到 AG-UI。
6. 代码执行要保留部分产物和透明错误，不要静态兜底。
7. 未来可以接远程 A2A、Docker sandbox、trace 页面，但都不是当前内核第一优先级。
8. 新一轮重构总纲见 [AgentHub-HiClaw-lite开源内核重构方案.md](./AgentHub-HiClaw-lite开源内核重构方案.md)。后续实现应优先按该方案收敛到 Matrix Room、CoordinatorRuntime、WorkerRuntime、ArtifactStore、GatewayAdapter 和 Controller/Reconciler，不要继续给旧流程补无限兼容。
9. 底层要从 `messages.ts -> OrchestratorEngine` 的过程式链路迁移到 HiClaw-lite 资源控制平面；第一批切片是 RoomService + Matrix Adapter、ManagerRuntime、WorkerRuntime 和 ArtifactStore，而不是继续扩大旧 RunEvent / TaskThread metadata 拼接。
10. 前端恢复路径已经开始改成“服务端 snapshot 优先”：`runtimeActivitySnapshot` 前推到 run detail，`TaskThread` 的 `prepared / assigned / active` 语义保留到子对话入口和 Agent tabs；同时 `agenthub.task.status` 也开始直接携带线程语义，后续继续减少浏览器本地二次拼接。
11. 后端控制面已开始真正接管 task 生命周期：`RunController` 现在除了 run lifecycle，还接住了 running-task resume requeue、blocked task 投影，以及 `executeTask()` 的 `task.assigned / task.started / task.completed / task.failed / task.cancelled` 统一落库、线程状态同步和事件广播。
11. `retry / replan` 的第一批旧散写也开始进入控制面：手动 retry、`retry_with_backoff`、`local_replan`、`agent_substitution` 的 task reset 已经改成统一走 `RunController`，让“任务回到 prepared 并等待重新执行”开始成为明确的控制面事实。
12. 动态新增任务与批量取消也开始往控制面收口：`supervisor supplement / task_split / global_replan` 的 `task.queued` 注入已经开始统一走 `RunController.queueTask()`；run 级取消现在也会同步更新对应 `TaskThread` 和子对话 metadata，而不只是改 task 表。
13. 动态任务注册入口继续收紧：`supervisor supplement / task_split / global_replan` 现在开始共用同一条“动态任务注册”路径，统一做任务资源入账、子对话关联、计划内存态同步和调度器纳管，减少 `plan.tasks.push / scheduler.addTasksToRun / 单独 executePlan` 分散散写。
14. 透明协作的第一层开始落地：任务子对话不再只剩 bootstrap、原始 prompt 和最终结果；`Manager 分派任务` 与 `Worker 接单开工` 已开始投影成可见消息，Worker 在主群聊也会发布真实开始执行、显式进度、澄清请求和节制心跳，向 HiClaw 式“内部协作也像 IM 时间线一样可审计”继续靠拢。
15. 运行中的 Human-in-the-Loop 已有第一条真实链路：如果群聊已有活跃 run，用户在主群聊追加约束时，不会再默认重开 run；消息会被登记为当前 run 的 `human_interrupt`，同步写入 blackboard、run events，并由 Manager 在主群聊和活跃 TaskThread 中可见确认。
16. 这条 HITL 链路已经真正接入控制面：`RunController.reconcile()` 现在会消费未处理的 `human_interrupt`，把新约束并入未完成任务描述，登记 `manager_actions/human_interrupts/*`，并发出 `run.replanned(strategy=human_interrupt)` 与 `task.rework_requested` 事件。对于被打断的 active task，它还会把 `workspace_task` 重置回 `pending`、把 `TaskThread` 重置回 `prepared`，让“人类插话后回到 Manager 手里再继续”成为真实运行时状态，而不只是消息记录。
17. TaskThread 级 Human-in-the-Loop 也已经接入同一条控制面：用户进入某个 `orchestrator-task` 子对话后追加纠偏，不再被当成普通 Agent 私聊回复；系统会精确按该 TaskThread 绑定的 `runId` 写入 `human_interrupt`，并在 blackboard / RunEvent 中带上 `source=task_thread`、`taskThreadId`、`taskId`、`childSessionId`，主群聊和任务房间都会看到 Manager 的可见确认。
18. Worker 中断链路已经进入新控制面：Manager 处理 `human_interrupt` 时，会对 active task room 执行 live interrupt，把对应 `RuntimeLease` 经 `RuntimeLeaseController` 标成 stale，并把 `WorkerInstance` 收回到 idle；任务会回到 `prepared`，再由 ManagerLoop / WorkerRuntime 接回执行。旧 `TaskExecutionService -> LocalA2ATransport` 已删除，cancel/abort 后续只能继续在 `RunController` / `WorkerRuntimeService` / 进程生命周期管理中补齐。
19. 左侧会话树对 `prepared` TaskThread 的口径也开始和控制面对齐：只要是绑定了 `groupSessionId + orchestratorRunId + orchestratorTaskId` 的 `orchestrator-task` 子对话，即使还没有 `workspaceAgentId`，也会被当成稳定的群聊子线程显示和展开，不再因为”尚未正式分配 Agent”被当成临时预览项或直接隐藏。
20. 群聊消息入口继续削弱“非 mention 消息默认先过 Orchestrator 网关”的痕迹：用户明确回复某条 Worker 房间消息时，会直接由对应活跃 Worker 接话；普通运行中补充要求仍进入当前 run 的 `human_interrupt` 控制面，避免绕过审计、黑板和 TaskThread 同步。
21. **WorkerController reconcile 模式已对齐 HiClaw**：`WorkerController` 实现分阶段 reconcile loop（EnsureReady → AssignLease → ObserveHealth → RecoverStale），每阶段幂等检查当前状态 vs 期望状态，仅在有差异时行动。Worker 状态始终从 reconcile 写回，不再分散在多处散写。
22. **HiClaw 风格 idle-stop 机制已落地**：空闲超过 30 分钟的 Worker 自动转入 sleeping 状态，保留 TaskThread 和配置不动。新任务到来时通过 `ensureReadyForTask()` 自动 wake + reconcile 到 ready。服务重启时通过 `recoverStaleOnStartup()` 恢复所有活跃 lease 并标记 stale。
23. **Worker 心跳监控**：2 分钟宽限期 + 5 分钟超时检测，避免误杀刚启动的 Worker。超时后自动标记 Worker failed + 对应 runtimeLease stale，确保死掉的 Worker 不会永远占着”正在执行”的状态。
24. **Manager 主动巡检（ManagerPatrol）已落地并开始进入 Room timeline**：每 2 分钟自动扫描所有 active run，检查 Worker 健康状态和任务超时。检测到死 Worker（8 分钟无心跳）或任务超时（10 分钟无完成）时，自动标记资源状态、发 RunEvent、并在群聊中发出可见的进度检查消息。最新收口后，`manager-patrol-check` 也会写入 group room 的 `manager.message` 和 task room 的 `task.progress` timeline event，刷新和切换子对话后仍可审计；Patrol 现在还会按当前 run 的 TaskThread worker 集合过滤 busy Worker，避免一个 run 的巡检误处理另一个 run 的全局 busy Worker。
25. **ArtifactStore 收敛为产物唯一事实源**：`ArtifactController.registerArtifactBatch()` 成为产物唯一注册入口，每次注册自动发 `artifact.created` RunEvent。`orchestrator-engine` 在 `materializeArtifactHandoffs` 之后自动批量注册产物。`workspace_tasks.artifacts` JSON 字段降级为缓存，可通过 `syncTaskArtifactsCache()` 从 artifacts 表重建。
26. **共享任务结果契约开始进入 Manager 验收链路**：`.agenthub/shared/tasks/{taskId}/spec.md` 现在会明确要求 Worker 使用 `STATUS / SUMMARY / DELIVERABLES / NOTES` 写 `result.md`；后端写入 completed / failed / cancelled / blocked 终态时也会生成同一格式。最终汇总前会读取并校验 `result.md`，把 `SUCCESS / REVISION_NEEDED / BLOCKED / INTERRUPTED` 映射回 `workspace_tasks`、`TaskThread` 和 RunEvent 状态；如果结果契约非法，会发出 `manager.reviewed` 警告并把任务纳入交付复核。
27. **RunEvent replay API 完整化**：`GET /api/orchestrator-runs/:id/events?afterSequence=N` 支持增量重放，`afterSequence=0` 时附带完整资源 snapshot（tasks/taskThreads/runtimeLeases/artifacts/workerInstances + counts），前端可从事件流恢复完整运行态。
28. **ManagerLoop.step() Observe-Think-Act 主循环已落地**：`managerLoopStep()` 观察 run 内任务状态，自动决定下一步动作（dispatch_pending / review_running / synthesize / waiting / blocked），接入 RunController.reconcile() 和 ManagerPatrol，让"Manager 在持续经营任务"成为真实运行态而非概念。
29. **Planner 已从主路径退下**：复杂任务的初始计划生成不再调用旧 `Planner.createPlan()` 作为必经主脑，而是进入 `manager-planner.ts` 的 Manager-first 行动方案生成。旧 `planner.ts` 仍保留 JSON 抽取、计划校验、任务契约归一化等兼容工具，后续应继续拆成纯工具模块或 planning skill。
30. **HiClaw-lite Phase 0 护栏已开始落地**：`OrchestratorEngine` 和 `LocalA2ATransport` 已在代码中标注为迁移期兼容层。后续新 Manager 决策、Room 语义、生命周期所有权和内部通信主线不应继续往这两个旧模块里扩。
31. **RoomService / MatrixRoomAdapter 第一版已落地**：数据库新增 `rooms`、`room_participants`、`timeline_events`；服务层新增 `RoomService`、`MatrixRoomAdapter`、`LocalMatrixCompatibleRoomAdapter` 和 `/api/rooms`。`MatrixRoomAdapter` 已开始通过 Matrix Client-Server API 创建真实 room、发送 `m.room.message`、记录 Matrix `room_id / event_id / user_id`，并为 Human / Manager / Worker 生成 Matrix participant id。`LocalMatrixCompatibleRoomAdapter` 只作为测试/开发 fallback，不再被称为目标通信层。
32. **CoordinatorRuntime 正在从内部 LLM 壳转向 OpenClaw/QwenPaw Manager runtime**：新增 `CoordinatorRuntime` action schema、`CoordinatorService.stepRoom()` 和 Manager 配置目录化。Manager workspace 会生成 `SOUL.md`、`AGENTS.md`、`skills/`、`workers-registry.json`、`state.json`；内置第一批 skill 契约包括 `worker-management`、`task-management`、`channel-management`、`file-sync-management`、`human-management`，每个 skill 都按“自然语言理解 -> 调 Controller API -> 写回 Matrix room”的模式描述。`resolveCoordinatorRuntime()` 默认已转向 `openclaw`；`local-llm` 仅允许显式选择作为迁移/测试 fallback，不能再作为 Manager 主路径。
33. **Coordinator assign -> task room -> WorkerRuntime 的任务闭环已跑通**：Coordinator 返回 `assign` 时，系统会创建真实 run / workspace task / TaskThread / task room / Worker participant / RuntimeLease，并异步启动 `WorkerRuntimeService.runTaskRoom()`。Worker 进度、结果和 artifact.created 会写入 task room timeline，ArtifactStore 会登记 object key；RunController 会同步 `assigned / active / completed / failed / cancelled` 状态。动态 `OrchestratorPlan` 成功后也已开始优先翻译成 Coordinator assign batch，复用同一个 Manager run 创建 task room / RuntimeLease / ArtifactStore 记录并通过 WorkerRuntime 执行，不再直接进入旧 `OrchestratorEngine.startRun()`。运行详情页的单任务 retry 也已切到 `WorkerRuntimeService.rerunTaskRoom()`：先通过 `RunController.resetTaskForRetry()` 重置资源，再从已有 task room 重新接单，不再调用旧 `OrchestratorEngine.retryTask()`。
34. **MinIO/S3-compatible ArtifactStore object-key 最小闭环已落地**：`artifacts` 表已补 `roomId / storageProvider / bucket / objectKey / storagePath`；`registerTaskArtifact()` 会按 S3-compatible object key 语义把文件、内联内容或 descriptor materialize 到 S3/MinIO（配置 `AGENTHUB_OBJECT_STORE_PROVIDER=s3`）或本地 fallback object store；`WorkerRuntimeService` 的 `artifact.created` timeline event 已绑定真实 `artifactId / objectKey / storagePath`。
34.1. **共享任务契约已从本地目录依赖中解耦**：`prepareSharedTaskDirectory()` 现在即使没有项目工作区，也会发布 `shared/tasks/{taskId}/meta.json`、`spec.md`、`plan.md`；任务终态会发布 `result.md`。有项目路径时才额外镜像到 `.agenthub/shared/tasks/{taskId}/`。这让 Matrix @mention + shared object refs 成为主交接方式，而不是要求 Worker 猜本地相对路径。
35. **Room timeline replay + realtime WS 最小投影链路已落地**：前端新增 `/api/rooms` typed client 与 `roomTimeline` 纯投影模块；`chatStore.selectSession()` 会 ensure 当前 group/direct/task-thread Room，拉取 participants + timeline，把 `manager.message / worker.message / task.assigned / task.progress / artifact.created` 投影为现有消息列表、任务看板、Agent tabs 和产物卡可消费的数据。服务端 `RoomService.appendTimelineEvent()` 现在会广播 `room:timeline` WebSocket 事件；task room event 会同时通知对应 task session 和父 group session，前端收到后复用同一套投影函数实时更新子对话消息缓存、任务看板和 artifact 卡。即使旧 run snapshot / plan 还没有到达，Room timeline 的 `task.assigned / task.progress` 事件也能先创建最小任务看板、Agent tab 和稳定 task room 入口。Manager 的 `manager-review-started` / `manager-final-review` 也会从 Room timeline 投影成 `agenthub.run.status(synthesizing/completed/failed)`，让刷新或重放时能恢复“正在汇总/最终复盘”状态。刷新、切换会话或实时执行过程中，Room timeline 中的 Manager/Worker 过程消息、run 状态与 ArtifactStore object key 不会只停留在后端。
36. **Coordinator 多 assign 已进入同一个 shared run**：Coordinator 一次返回多个 `assign` 时，`room-chat-bridge` 不再循环调用单任务派发、制造多个孤立 run，而是通过 `dispatchCoordinatorAssignBatch()` 创建一个 run，并在其下创建多个 `workspace_tasks / TaskThread / task room / RuntimeLease`。每个 Worker 仍在自己的 task room timeline 中接单、汇报进度和登记 artifact；整个 run 只在所有 Worker 任务 settle 后统一 `completed / failed / cancelled`。这让“Manager 带团队完成一个用户目标”开始成为真实控制面语义，而不是多个单任务拼在一起。
37. **Coordinator assign 已具备最小依赖账本语义**：`CoordinatorAction` 现在支持 `taskKey / dependsOn`。批量派发会先校验重复 key、缺失依赖和环形依赖，再把 `dependsOn` 转换成真实 `workspace_tasks.dependencies` task id，并写入 Room timeline assignment metadata 和 run plan。WorkerRuntime 执行不再永远全并发，而是按依赖层推进；如果上游失败或取消，下游 task room 会留下 `worker-runtime.skipped-by-dependency` timeline event，并把任务标成 `skipped-by-dependency` 失败态，避免没有前置产物还硬跑。
38. **WorkerRuntime task room 过程事件更完整**：`WorkerRuntimeEvent` 新增 `clarification` 和 artifact `status`。Worker 可以在 task room 中发出澄清请求，服务端会写入 `approval.requested` timeline event，metadata 中保留 `question / options`；Worker 也可以登记 `partial` artifact，ArtifactStore 会以 `partial` 状态保存 object key，timeline 的 `artifact.created` 事件也会携带 canonical artifact。这样失败或等待用户确认时，部分产物和澄清上下文不会丢。
39. **Worker 澄清已经进入真实等待人类资源状态**：澄清不再被当成普通失败。`WorkerRuntimeResult.status` 支持 `waiting_for_human`；`TaskThread.status`、`RuntimeLease.status`、`WorkerInstance.observedState` 会同步进入 `waiting_for_human`；`RunController.markTaskWaitingForHuman()` 会把对应 task 标成 `blocked + progressStatus=awaiting_human_clarification` 并发出 `approval.requested` RunEvent，run 本身保持 `running`。依赖链上如果上游正在等待人类澄清，下游会暂停为 `waiting_on_dependency_human_clarification`，不会误报为依赖失败。
40. **任务房间澄清回答的最小 resume path 已打通并开始资源化**：用户在 `orchestrator-task` 子对话里回复 Worker 澄清时，消息会先作为 `human.message` 写入 task room timeline；如果该 room 存在未被 resume/completed 覆盖的 `worker-runtime.clarification-requested`，`room-chat-bridge` 会把对应 `task_clarifications` 记录从 `pending` 更新为 `answered`，写入 `worker-runtime.resume-requested`，并可重新调用 `WorkerRuntimeService.runTaskRoom()`，让 Worker 带着用户回答继续执行、继续登记进度和 artifact。这是 HiClaw 式 Human-in-the-Loop 从“可见”走向“可介入后继续”的第一条 Room 原生链路。
41. **HITL 与依赖等待态已进入前端 Room timeline 投影**：`roomTimeline` 现在会把 Worker 的 `approval.requested` 澄清请求、`worker-runtime.waiting-for-human` 进度事件，以及 `worker-runtime.waiting-on-human-dependency` 依赖等待事件投影为 `agenthub.task.status(status=blocked, taskThreadStatus=waiting_for_human)`。`worker-runtime.skipped-by-dependency` 会投影为 `failed`，不会在看板上继续假装 running。`chatStore`、Agent tabs、Header 和 TaskBoard 都能把等待补充/依赖跳过显示成真实状态，并保持 task room 入口稳定存在。
42. **HITL resume 边界已加测试保护**：`worker-runtime.test.ts` 已覆盖“同一条人类回答不会重复 resume 同一个 clarification”和“Worker 恢复后可以再次提出澄清并继续保持资源等待态”。这能防止 task room 因重复点击、WS 重放或二次追问而重复启动 Worker、重复产物或误把 run 标成 completed/failed。
43. **动态计划初始分发已切到 Coordinator assign batch**：`messages.ts` 中动态计划成功后会通过 `startPlanRunWithCoordinatorAssignBatch()` 把 `OrchestratorPlan.tasks` 转成 Coordinator `assign` actions，复用已有 Manager run，校验不能派给 Orchestrator，并通过 `dispatchCoordinatorAssignBatch()` 创建 task room、RuntimeLease 和 WorkerRuntime 执行链路。`tests/dynamic-plan-coordinator-dispatch.test.ts` 已覆盖这条新入口。
44. **运行详情页 retry 已切到 WorkerRuntime task room**：`POST /api/orchestrator-runs/:id/retry-task/:taskId` 不再 `new OrchestratorEngine().retryTask()`，而是要求任务具备 TaskThread/task room，调用 `RunController.resetTaskForRetry()` 后通过 `WorkerRuntimeService.rerunTaskRoom()` 重新执行。老数据没有 task room 时会透明返回 409，而不是偷偷回旧引擎。
45. **运行中人工干预已切到 Room timeline + RunController**：`processPendingHumanInterrupts()` 不再调用 `OrchestratorEngine.applyHumanInterruptToActiveRun()` 去改旧内存计划。用户在主群聊或 task room 中补充要求后，Manager 会把处理结果写入 group room / task room timeline，同时由 RunController 侧资源状态标记任务返工、active Worker 中断、RuntimeLease stale、WorkerInstance idle，保留完整可审计轨迹。
46. **运行取消和服务启动恢复不再回旧 Engine**：运行详情页 cancel 不再调用 `OrchestratorEngine.cancelActiveRun()`，只走 `RunController.cancel()`；服务启动时不再 `OrchestratorEngine.resumeRun()`，而是把 running task 通过 `RunController.requeueRunningTasksForResume()` 重新挂回 prepared，再 `RunController.reconcile()` 触发 ManagerLoop。旧 Engine 的外部入口进一步收缩到迁移期复杂执行兼容层内部。
47. **终态 run 的最终复盘已进入 ManagerLoop + CoordinatorRuntime resource-review skill + Room timeline 主线**：当 `managerLoopStep()` 观察到 run 下所有任务都到达终态后，会先发 `run.synthesizing`，并写入 `manager-review-started` group room timeline event；随后从 `workspace_tasks`、`TaskThread`、task room timeline、ArtifactStore 和共享任务 `result.md` 读取事实，并交给 `coordinator-runtime/final-review-skill.ts` 生成透明的确定性 `Manager 最终复盘`。复盘会写入 group room timeline，并兼容镜像到旧 `messages` 表，最后发出 `run.completed` 或 `run.failed`。前端 Room timeline replay 会把 review started/final review 投影为 run status。这条路径不再调用旧 `OrchestratorEngine.synthesizeAndReport()`；后续要把这个 resource-review skill 升级为可选模型化 review / OpenClaw skill，而不是回到旧 Engine。
48. **新内核验收口径继续收口**：smoke 测试里最后两处直接 `new OrchestratorEngine()` 的旧主路径验证已经移除。`manager-interrupted active task rooms are requeued by RunController and resumed by WorkerRuntime` 现在验证 `human_interrupt -> RunController.reconcile() -> task/TaskThread prepared -> RuntimeLease stale -> WorkerInstance idle -> WorkerRuntimeService.rerunTaskRoom()`；`retry task re-enters run execution lifecycle through task room WorkerRuntime` 现在验证运行详情页 retry route 通过已有 task room 和 `WorkerRuntimeService.rerunTaskRoom()` 完成，而不是调用旧 `OrchestratorEngine.retryTask()`。
49. **Phase 0 / Phase 6 防回流测试已补上并加严**：`tests/hiclaw-lite-boundary.test.ts` 把旧执行链边界固化成自动化测试。`TaskExecutionService` 只能被 `orchestrator-engine.ts` 这个迁移层引用，`LocalA2ATransport` 只能被 `task-execution-service.ts` 引用；`rooms / coordinator-runtime / worker-runtime` 这些新内核模块不得引用 `a2a-internal` 或 `local-a2a-transport` 作为内部任务通信路径。最新还增加了 lifecycle controller 边界：`index.ts`、`manager-loop`、`manager-patrol`、`task-thread-service`、`run-controller`、`rooms / coordinator-runtime / worker-runtime` 不得直接调用 RuntimeLease persistence helper，必须通过 `RuntimeLeaseController`。后续如果有人把旧 A2A/TaskExecutionService 或绕过 controller 的 lease helper 接回新主线，测试会直接失败。
50. **ManagerLoop 已能原生派发 prepared task room**：`managerLoopStep()` 现在观察到 `pending/blocked` 且具备 `prepared` TaskThread 的任务时，会确保 task room、Worker participant，写入 `manager-loop.dispatch` 的 `task.assigned` timeline event，然后调用 `WorkerRuntimeService.rerunTaskRoom(source=manager-loop.dispatch-pending)`。这让人工打断、服务恢复、retry/replan 后重新回到 `prepared` 的任务，不再只停在“等待调度器或外部触发”，而是能由 ManagerLoop 自己重新交给 WorkerRuntime。`awaiting_human_clarification` 的 blocked task 会保持 waiting，不会被误重启。
51. **WorkerRuntimeService.runTaskRoom() 已收口为完整任务房间生命周期入口**：直接 `runTaskRoom()`、`rerunTaskRoom()`、澄清 resume、Coordinator assign、动态计划分发和 ManagerLoop prepared-task 派发现在共享同一条生命周期路径。WorkerRuntime 一开始就会写入 `worker-runtime.started` timeline event，并同步把 `workspace_task` 标为 `running`、`TaskThread` 标为 `active`、`RuntimeLease` 标为 `running`、`WorkerInstance` 标为 `busy`；运行中会写入 `worker-runtime.heartbeat` task room timeline event 并刷新 WorkerInstance `lastHeartbeatAt`，最终 completed / failed / cancelled / waiting_for_human 也在 `runTaskRoom()` 内部统一同步到 RunController 和资源状态。前端 Room timeline 投影已经把 `worker-runtime.started` 锁定成 `agenthub.task.status(status=running, taskThreadStatus=active, progressPercent=5)`，减少“用户发起任务后看不到谁开工”的空白感。
52. **Phase 6 Controller/Reconciler 第一轮已完成**：新增 `RoomController` 和 `RuntimeLeaseController`，并把启动/关闭恢复、Coordinator assign、WorkerRuntime、ManagerLoop、ManagerPatrol、TaskThread 准备路径切到 controller surface。`RoomController` 负责 group/task room reconcile 和 Worker participant 绑定；`RuntimeLeaseController` 负责 lease create/ready/running/waiting/release/fail/stale/recovery。`RunController` 注释和职责口径也已更新为 Run lifecycle owner，不再把旧 `OrchestratorEngine` 写成当前执行主路径。
53. **迁移兼容层已删除**：`OrchestratorEngine`（4447 行）、`TaskExecutionService`（400 行）、`LocalA2ATransport`（42 行）已全部删除。确认零外部调用者——整个 `apps/server/src/` 中无任何文件 import 这三个模块。边界测试 `hiclaw-lite-boundary.test.ts` 已更新为验证这些文件不会被重新引入。相关 smoke test 中测试死代码的用例已移除。AGENTS.md 和 CLAUDE.md 已更新。所有任务执行现在通过 `RunController` / `ManagerLoop` / `WorkerRuntimeService` / `CoordinatorRuntime` / `RoomService` / `ArtifactStore`。

## 当前最重要的不足

- 我们现在还更像“多 Agent 编排工作台”，还不像 Coze 那样完整的 AI 工作平台。
- 和 HiClaw 相比，我们还没有完全做到”Manager 通过 skills 操作控制平面”。当前已生成 Manager workspace 和第一批 AgentHub 版 skill 契约，但真实 OpenClaw/QwenPaw Manager 进程、Matrix 消息监听、skill 调 Controller API 的端到端闭环还需要继续推进。
- TaskThread 已开始成为稳定子对话，也已经支持 Human 在任务房间里插话并进入 Manager 控制面；`RoomService` 已提供真实 Matrix adapter + 本地 fallback 的 Room / Participant / TimelineEvent 资源层，前端也有了 Room timeline replay + realtime WS 最小投影链路，并能在旧 snapshot 缺席时从 Room task event 生成最小任务入口。但真实 Matrix 用户注册、每 participant access token、invite/join/多身份发言和长期 Worker Matrix listener 还需要继续做。
- `CoordinatorRuntime` 已经能在群聊入口处理自然回复、澄清、补员建议，以及一个 Manager 决策内的单个或多个 `assign` 真实派工闭环；多个 `assign` 会共享同一个 run 并创建多个 task room，并已支持 `taskKey / dependsOn` 的最小依赖账本和按层执行。动态计划的初始分发、运行详情页 retry、运行中人工干预、run cancel、服务启动恢复、终态 run 最终复盘都已开始切到 Coordinator/WorkerRuntime/RunController/Room timeline 主线；终态复盘的文本构造已从 `ManagerLoop` 硬编码抽到 `coordinator-runtime/final-review-skill.ts`，但目前仍是确定性 resource review。旧 `TaskScheduler` 已删除，冲突合并后的后续动作、模型化 review skill 和复杂返工调度只能继续进入 `ManagerLoop` / `RunController`，OpenClaw / QwenPaw adapter 也尚未接入。
- `WorkerRuntimeService` 目前证明了 task room 接单、timeline 写回、澄清请求、`task_clarifications` pending/answered 资源记录、TaskThread/RuntimeLease/WorkerInstance 的 `waiting_for_human` 等待态、partial artifact、用户回答澄清后的最小 resume、失败后 rerun，以及 ArtifactStore 注册，并已被 Coordinator assign、动态计划初始分发、运行详情页单任务 retry 和 ManagerLoop prepared-task 原生派发主线调用；前端 Room timeline 投影也已经能把 `approval.requested / waiting_for_human` 显示为“等待补充”。但 resume/rerun 仍是 bridge/service 层的一次性恢复调用，还没有成为长期 Worker runtime 的原生等待/恢复状态机。旧 `TaskExecutionService -> LocalA2ATransport` 已删除。
- ArtifactStore 已具备 local filesystem object-key 最小语义，前端产物卡和任务看板已经可以从 Room timeline 的 `artifact.created` replay 与 `room:timeline` realtime event 中读取 object key / storage provider / storage path；但完整 Asset Center、跨 run 资产索引和旧 snapshot/message metadata 的下线仍未完成。
- `.agenthub/shared/tasks/{taskId}` 已建立，`result.md` 已开始参与最终验收和状态同步；但 shared task directory 还要继续从“执行契约目录”升级成完整协作空间：`spec.md / plan.md / result.md / artifacts` 要贯穿分配、执行、验收、返工和下游接力，并逐步前移到 ManagerLoop 的 review 阶段。
- WorkerInstance / RuntimeLease 已经有第一轮 controller ownership：Worker ensure-ready、heartbeat、stale recovery、idle-stop、startup/shutdown lease recovery、task room running/waiting/released/stale 都已经进入 `WorkerController` / `RuntimeLeaseController`。和 HiClaw Worker CRD 的差距主要剩在 runtime reconfigure、per-agent config/cache/session 隔离做实、长期 Worker 等待/恢复状态机和更完整的 reconcile queue。
- 凭证和能力控制面还比较初级。HiClaw 通过 Higress consumer 隔离真实凭证；AgentHub 近期至少要继续推进 RuntimeLease 级最小 env 注入、secret redaction、per-agent/per-task MCP scope，长期再考虑 gateway provider。
- 运行态反馈仍需要继续打磨，但关键空白点已开始收窄：群聊消息进入 CoordinatorRuntime 前会先写入 `coordinator.observing`，WorkerRuntime started 事件也会立刻推动 task/thread/lease/worker 进入 active/running/busy，并通过 Room timeline 投影到看板和 Agent tabs；WorkerRuntime 运行中 heartbeat、依赖等待/跳过、ManagerPatrol 的任务超时和 Worker 异常、Manager review started/final review 都已进入 group/task room timeline，并能投影成明确 UI 状态。下一步要把更复杂的返工/重排/模型化 review 也统一成同样连续的 Room timeline 事件。
- 子对话、进度、产物之间还需要更强的事件一致性。
- 当前 `human_interrupt` 已经能打断 active worker，把任务重新挂回 Manager 控制面，并在 group/task room timeline 中留下可见轨迹；`ManagerLoop.step()` 也已能把回到 prepared 的 task room 再次派给 WorkerRuntime。但“更复杂的多任务批量重排 / 更细粒度的局部 resume / 更强的人机接管策略”还没有完全闭环，后续要继续把这部分升级成更完整的 Manager skill 与 Worker lifecycle control。
- `OrchestratorEngine`、`TaskExecutionService`、`LocalA2ATransport`、`TaskScheduler` 已删除；剩余风险不再是旧文件本身，而是旧 snapshot/message metadata、旧 AG-UI cache 和部分 retry/replan/resume 桥接逻辑里仍可能残留 DAG-first 心智。后续应把复杂返工、重排、模型化 review、长期 Worker 等待/恢复继续收进 `ManagerLoop` / `RunController` / `WorkerRuntimeService`，并用边界测试防止旧入口复活。
- Run lifecycle 已有 start/dispatch/running/synthesizing/finish/cancel/retry/requeue/reconcile 的控制面，但暂停、恢复、长期清理、trace 贯通和 durable reconcile queue 还需要继续补。
- 远程 A2A、MCP 能力、Skills/Rules 注入还需要更完整的产品化。
- 评估体系还不够，必须能证明多 Agent 协作为什么比单 Agent 更强。
- 群聊创建已经开始支持“群聊目标 + 轻量组队建议”；群聊内动态补员走 Orchestrator `memberProposals` + 用户确认，不走前端关键词规则。
- Space / Task Center / Asset Center / Expert Center 还没有形成统一产品壳。
