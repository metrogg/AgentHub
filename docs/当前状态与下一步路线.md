# 当前状态与下一步路线

最后更新：2026-06-07

这份文档是 AgentHub 当前的“事实总览”。它的目的不是讲历史，而是让开发者和 AI Agent 先对齐现在到底在做什么、什么已经定了、什么还在推进。

## 当前一句话定位

AgentHub 当前运行时主路径是 IM 式多 Coding Agent 协作，产品北极星是 `Coze 风格的开源 AI 工作平台`。聊天页、任务子对话、任务看板和产物卡的事实源正在统一到 `Room timeline + Resource snapshot`。

用户在群聊里提出目标，Manager / Orchestrator 像团队负责人一样理解意图，决定回复、追问、补员、组队、派活或总结；多个 Coding Agent 在真实子对话里执行，主群聊展示 Manager 的计划、进度、成员回报、产物和最终汇总。后续会在这条主路径之上继续长出 Space、Task Center、Asset Center、Expert Center 和 Eval / Trace。

底层重构方向已经进一步收敛为 AgentHub Product Shell + Lightweight HiClaw Kernel：前端继续保留 AgentHub 自己的 Coze / Kimi 风格操作界面，底层学习 HiClaw 的 Room / Manager / Worker / HITL 架构范式，但产品部署形态采用嵌入式本地控制器：AgentHub Server 仍在本机作为 Controller API / UI backend / Room adapter 运行，Tuwunel、MinIO、OpenClaw Manager、OpenClaw Worker 可以进入 Docker resident runtime。自研 UI 替代 Element Web，本地 filesystem SharedStorage 仍是默认产物存储，MinIO/S3-compatible 是可切换 adapter。ClawTeam 新增为轻量实现参考：学习它的 CLI adapter/profile、git worktree、task claim lock、LeaderWatcher、profile doctor/test 和 board snapshot，但不采用它的文件 inbox 作为 AgentHub 内部主通信。通信层以 Matrix Room/timeline/participant/mention 语义为协作事实源，本地真实 Matrix 默认采用 Tuwunel，兼容连接已有 Synapse/Conduit；`TestRoomAdapter` 只允许自动化测试使用，不能作为开发/产品通信层或故障降级路径。Manager Runtime 学 OpenClaw / QwenPaw；Worker Runtime 继续强化 Claude Code / OpenCode / Codex / Gemini，并可补充 OpenClaw / QwenPaw Worker；共享存储默认本地 filesystem，但保持 MinIO/S3-compatible object key 语义，任务契约和产物以 `shared/tasks/{taskId}/...` object refs 为主；AI Gateway 抽象化，短期可接 LiteLLM，长期目标 Higress；A2A 暂不作为内部主通信路径，只保留为外部互操作或 Matrix event 中的可选任务语义 envelope。后续要逐步把 `Room`、`Run`、`Task`、`WorkerInstance`、`Artifact`、`RuntimeLease`、`TimelineEvent` 做成一等资源。

最新的 HiClaw wiki 深读结论已经同步到 `docs/HiClaw架构调研与AgentHub底层重构方案.md`：我们要学的是 Manager-Workers 协作范式、Room 作为真实通信资源、shared task directory 作为任务协作空间、Worker 作为可协调资源、Human-in-the-Loop 作为一等参与者，以及 Gateway/consumer 风格的凭证隔离。ClawTeam 三方对比见 [AgentHub-vs-HiClaw-vs-ClawTeam-对比分析报告.md](./AgentHub-vs-HiClaw-vs-ClawTeam-对比分析报告.md)：它适合补 AgentHub 第一阶段的轻量执行可靠性，不适合替代 Matrix/HiClaw-style 透明协作内核。后续可以直接参考 [hiclaw-wiki.agent.final.md](./hiclaw-wiki.agent.final.md)、本地 [../hiclaw源码参考/](../hiclaw源码参考/) 和 [../clawteam源码/ClawTeam/](../clawteam源码/ClawTeam/)；不要把它简化成“做几个子对话”“加一个任务看板”或“用文件队列代替真实通信”。

当前仍处开发阶段，旧会话、旧任务、旧数据库和旧 workspace/storage 数据不再是架构约束。旧数据能低成本只读展示就展示，不能展示可以清除重建；不允许为了旧数据保留旧流程、旧入口或旧 schema。

## 2026-06-07 最新现场状态

- **本机 HiClaw-lite 主线已经进入可实测阶段**：开发启动脚本会写入 `.agenthub-port` 并固定前后端目标；设置页“控制台 / 本机诊断”可以查看 Matrix、Manager Runtime、Controller Plane、容器运行时和沙箱状态。当前现场可看到 OpenClaw Manager 以本地 resident process 运行，通过真实 Matrix `/sync` 接入房间；Manager workspace 位于 `%LOCALAPPDATA%/AgentHub/manager/global`，配置文件为 `openclaw.json`，Manager persona / `agenthub-controller` skill / Controller API 可达性会在设置页展示。
- **Manager 身份与 room binding 已基本打通，但仍要继续清理历史房间**：新的 group room 可以绑定到 resident Manager 的 Matrix identity，`roomBindings` 会显示 `configured / bound`；部分旧 direct room 或早期 group room 仍可能显示 `unbound`，这通常表示该 room 里的 Manager participant 不是当前 resident Manager identity，应该通过 room reconcile / 新建 room / 重建 binding 收口，而不是让旧身份继续混用。
- **Worker 现场问题已定位并修复第一刀**：当前群聊里的“高级前端工程师”和“产品经理”都曾以 `runtimeBase=opencode` 创建但 `modelId=null`，导致一个 Worker 被 `WorkerController` 判定为 `failed: No model configured for this worker`，另一个 Worker 通过旧 group mention bridge 执行失败后又被错误回写成 `idle`。现在两者已补齐 `mimo-v2.5` 模型绑定，并重新 reconcile 到 `listening`。
- **Worker 创建链路已加硬约束**：`ControllerApi.createWorker()` 现在要求新 Worker 必须有显式模型绑定，或存在 `AGENTHUB_WORKER_LLM_MODEL / LLM_MODEL` 作为 Worker 模型来源；否则直接失败并暴露错误，不再创建一个注定会 failed 的 WorkerInstance。后续前端“添加 Worker / 组建群聊 / Manager 补员确认”也必须把模型选择带入 Controller API。
- **Worker 基座默认 Codex 的旧心智已收掉**：Manager 补员提案缺少 `workerRuntimeBase / codeAgentType` 时不再自动填 `codex`；`ControllerApi.createWorker()` 缺少 Worker runtime base 时会优先读 `AGENTHUB_WORKER_RUNTIME_BASE`，其次复用当前 workspace 已有 Worker 的基座，仍无法确定时直接报错。OpenClaw Worker 的 `codeAgentType` 不再被写成 `codex`，避免 UI/诊断把 OpenClaw resident Worker 和 Codex CLI 串台。
- **前端 Agent 配置也不再默认 Codex**：新建 Agent、Agent library normalize、专家模板导入和 Coding Tools 启动修复都不会再把缺失的 Worker 基座补成 Codex。普通 Worker 可以处于“未选择 Worker 基座”的未配置态，保存后由 Controller / 运行前校验显式要求补齐 runtime base 和模型；显式 Codex 专家模板仍然保留 Codex，因为那是模板自己的选择。
- **Member Reconcile 5 阶段已进入主创建链路**：新增 `apps/server/src/services/controller-plane/member-reconciler.ts`，`ControllerApi.createWorker()` 已统一走 `ResolveMemberSpec -> ApplyWorkspaceAgent -> ApplyWorkerInstance -> JoinRooms -> AnnounceAndObserve`。工作区“添加 Worker”接口会传入 `ownerId / createDirectSession / joinGroupRoom / announce`，由 Controller 负责创建/复用 WorkspaceAgent、创建 WorkerInstance、准备 runtime、加入 group/direct Matrix room、刷新 Worker contract，并由 Manager 在群聊里自然公告成员加入。接口返回 `stages / runtimeBase / groupRoom / directRoom / participants / announcements`，方便前端和 Manager skill 展示真实进度。
- **补员确认卡已接入真实创建链路**：用户确认 Manager 的 `memberProposals` 后，后端不再直接 insert `workspace_agents` 或手动 add participant，而是把 proposal / 专家预设中的角色说明、系统提示、skills、工具权限、上下文策略、`roleProfile` 和 Worker runtime base 交给 `ControllerApi.createWorker()`。确认卡 metadata 会保存 `workerInstanceIds / runtimeBases / memberReconcileResults`，后续前端可以直接展示每个成员卡在 Resolve / Apply / Join / Announce 的哪一步。
- **Manager `create_worker` action 已能真正创建并入群**：`ManagerRuntimeService` 现在不会再把 `create_worker` 当成普通 Manager 消息写出来，而是从 action metadata / `memberProposal` 规范化 member spec，调用 `ControllerApi.createWorker()`，走同一条 Member Reconcile，成功后写 `manager.action.create_worker.applied` 阶段结果，失败则在 Room timeline 写明确诊断。OpenClaw Manager workspace 内的 `agenthub worker create/apply` CLI 也改为必须显式 `--runtime-base`，不再隐藏默认 Codex。
- **SOUL/AGENTS/Skills/registry/state 规范化已落下第二刀**：新增 `apps/server/src/services/agent-contract/` 作为 Manager / Worker 统一 contract 生成层。Worker workspace 现在由 `ensureWorkerAgentContract()` 生成 `profile.json / runtime.json / SOUL.md / AGENTS.md / skills / state.json / rooms.json / tasks.json`，并向 `AGENTS.md` 幂等注入当前 Room、Controller、SharedStorage、runtime base、runtime mode、五阶段 Worker Reconcile 和任务契约上下文；`runtime.json` 也写入 `adapterContract`，说明 resident/bridge 的监听所有者、workspace contract、task contract 与 heartbeat 字段。Manager workspace 现在由 `ensureManagerAgentContract()` 生成 `runtime.json / SOUL.md / AGENTS.md / TOOLS.md / HEARTBEAT.md / skills / workers-registry.json / teams-registry.json / humans-registry.json / state.json / rooms.json / logs`，并镜像到 OpenClaw `agentDir`，让 OpenClaw Manager 真正读取同一套人格、规则、技能和 registry 文件。`ensureManagerAgentContractFromController()` 已开始从 Controller/DB 同步 active rooms、WorkerInstance、WorkspaceAgent、Matrix identity、Room participant、RuntimeLease、Human participant 和 active runs，刷新 `workers-registry.json / humans-registry.json / rooms.json / state.json`；OpenClaw Manager provider 启动/重启前会调用这条路径，不再只拿空 registry。`infra/manager-agent` 模板已补强 Runtime Architecture、Manager/Member/Worker 五阶段 reconcile、Bridge 规则、heartbeat patrol、显式 runtime/model 约束，以及 `review-and-synthesis / error-recovery / capacity-management / artifact-management / heartbeat / memory-management` 等轻量 Manager skill。`manager-runtime/manager-config.ts` 已降级为兼容外壳，正式生成逻辑不再散落在 provider/launcher 里。
- **Bridge Worker 也开始吃同一份 contract**：OpenCode / Claude Code / Codex / Gemini 这类 AgentHub-managed bridge Worker 执行前，会把 Controller 标准 Worker contract 投影到实际 CLI cwd：根目录 `AGENTS.md` 注入 `AGENTHUB:BRIDGE-RUNTIME-CONTEXT`，`.agenthub/worker-contract/` 下包含 `SOUL.md / profile.json / runtime.json / state.json / rooms.json / tasks.json / skills/`。这让 bridge 形态也能按 HiClaw-lite 的 SOUL/AGENTS/Skills 语义运行，而不是只靠一次性 prompt。
- **Worker Runtime 诊断已从“数量”升级为“逐个 Worker 可解释”**：`GET /api/settings/controller-plane/status` 现在会返回 `workerRuntimes[]`，包含每个 Worker 的 `resident-openclaw / resident-qwenpaw / bridge` 模式、runtime base、observed/desired state、Matrix identity、Room participant、listener owner、heartbeat、last error 和标准 contract 文件完整性。对 OpenCode / Claude Code / Codex / Gemini bridge Worker，还会运行 `inspectCodeAgentRuntime()`，检查 CLI 是否在 PATH、原生 `--version` probe 是否能启动、模型凭据、执行开关、cwd 和 blockers。设置页“AgentHub 内部 Controller Plane”会直接展示这些信息，方便判断某个 Worker 到底是常驻 OpenClaw、AgentHub-managed bridge，还是缺 Matrix 身份/缺 SOUL/AGENTS/skills/缺 CLI 配置。
- **Worker Runtime health 口径开始对等化**：Controller Plane 现在为每个 Worker 返回统一 `runtimeHealth`，不论它是 OpenClaw/QwenPaw resident 还是 OpenCode/Claude/Codex/Gemini bridge。Bridge health 来自 CLI 安装、native probe、模型/auth/config、执行开关和 cwd；resident health 来自 `WorkerBackend.inspect()` 的进程/容器状态；二者都会合并 contract ready、Matrix identity、WorkerInstance failed state 和 blockers。设置页 Worker runtime 行已经切到这组统一字段，减少“OpenClaw 看进程、OpenCode 看 CLI、页面各说各话”的割裂。
- **Resident Worker 自检入口已接入设置页和 Controller API**：`POST /api/settings/controller-plane/workers/:workerInstanceId/resident-self-test` 会按 HiClaw-lite contract 逐项检查 WorkerInstance、runtime base、WorkspaceAgent、`SOUL.md / AGENTS.md / profile.json / runtime.json / state.json / rooms.json / tasks.json / skills/`、Matrix identity、Room participant 和 resident backend health。设置页 Worker runtime 行对 OpenClaw/QwenPaw resident worker 显示 `Resident 自检`，默认只做 dry-run，不往房间写 probe 消息；接口也支持显式 `dispatch=true`，通过真实 Room @mention 发送 self-test request，并等待 Worker 从 Matrix timeline 回复 `TASK_COMPLETED / QUESTION / BLOCKED / PHASE_DONE`。这让“Worker 异常”不再只靠日志猜，而能拆成 contract、Matrix、Room、backend、协议回复五类问题。
- **Controller HTTP API 第一版已可供 Manager skills 调用**：`/api/controller/*` 现在受 Manager Matrix token 保护，覆盖 Worker、Run、Task、Room、RuntimeLease reconcile、Artifact、Team、Human、Workspace state、Status、Heartbeat 和通用 `reconcile`。其中 Room 控制面支持创建、列表、详情、participants、events timeline、append event、@mention participant 和 reconcile；`agenthub room create/events/mention` 已改为走 `/api/controller/rooms*`，不再绕到产品态 `/api/rooms`。这一步让 OpenClaw/QwenPaw Manager 更接近 HiClaw 的“自然语言 -> skill -> Controller API -> 操作真实资源 -> 写回 Matrix Room”模式。
- **Controller task assign 已从假上下文收口为真实控制面入口**：`POST /api/controller/tasks` 已经委托 `ControllerApi.assignTask()`，Manager skill 派活会创建或复用 group session，启动 Run，创建 `workspace_tasks / task_threads / task room / RuntimeLease`，写入 `shared/tasks/{taskId}/spec.md`，并在 task room 里发 Matrix @mention-first `task.assigned` 事件。路由层不再构造 `fakeMessage` 或 `controller-task-*` 兼容对象；测试已覆盖任务资源、Worker participant 和 `metadata.matrixExecutionBus=true / coordinationSource=matrix-mention`。
- **Matrix @mention 可读显示已修**：Matrix `m.mentions.user_ids` 继续保存真实 `@worker-...:agenthub.local` 供协议识别，但普通消息 body 改为显示 Room participant 的可读名称，例如 `@产品经理`，避免聊天页暴露一串 Matrix user id。
- **group @mention 状态覆盖 bug 已修复**：`WorkerRuntimeService.runGroupMentionRoom()` 现在会把真实 runtime result status 返回给 dispatcher；Worker 执行失败时保持 `failed`，不会再因为 append 了失败消息就被 `MatrixEventDispatcher` 当成 `completed` 并回写 `idle`。
- **OpenCode / Claude Code / Codex / Gemini 当前仍是 AgentHub-managed Worker bridge**：这些 Worker 已经通过真实 Room timeline 输入输出，且可以有 Matrix identity / listener，但执行仍主要由 AgentHub 服务托管 CLI 子进程；OpenClaw Worker 才是 resident Worker 的目标形态。短期必须在 UI 和诊断里明确标注 bridge/resident 区别，避免用户误以为所有 Worker 都已经是 HiClaw 原生常驻容器。
- **OpenClaw Worker room-aware config 已推进一刀**：本地进程和 Docker resident backend 在生成 `openclaw.json` 前会从 Controller 查询该 Worker 已加入的 Matrix rooms，把实际 `providerRoomId` 写入 `channels.matrix.groups`，并把同房间 human / manager Matrix user id 加入 `groupAllowFrom`；同时把这些 rooms 注入 Worker contract 的 `rooms.json / AGENTS.md`，让 OpenClaw config 与 AgentHub 标准 contract 对齐。下一步仍要做真实 OpenClaw Worker 自己 `/sync` 后端到端验收。
- **resident Worker 协议回写已接入 Controller 资源闭环**：当 OpenClaw/QwenPaw resident Worker 或其他基座通过 Matrix room 发回 `TASK_COMPLETED: ...`、`BLOCKED: ...`、`QUESTION: ...`、`PHASE{N}_DONE: ...` 时，`worker-result-listener` 会先按真实 `Room` 资源解析 `taskThreadId / taskId / runId / RuntimeLease / WorkerInstance`，不再错误地把 `room.id` 当成 `taskThreads.sessionId`。`TASK_COMPLETED` 会同步 task done、thread completed、lease released 和 Worker idle/listening；`QUESTION` 会创建 `task_clarifications`、写 `approval.requested` timeline event，并把 task/thread/lease/worker 全部置为 waiting-for-human；`BLOCKED` 会进入 RunController blocked 事件并释放 lease；阶段完成会进入 progress event。这是 resident Worker 真常驻之后能够被 Controller 正确认领结果的关键补口。
- **前端诊断面板完成一轮基础修整**：设置页 Manager Runtime 控制面已处理长路径、session key、provider error 文案挤爆布局的问题；但信息架构仍偏“诊断表”，后续应继续改成“状态摘要 + 关键异常 + 明细抽屉”的控制台，而不是把所有底层字段平铺给用户。

## 当前权威边界

- **Agent Runtime / Agent Base**：架构口径从 `Coding Tools` 收敛为 Agent 基座。OpenClaw / QwenPaw 优先作为 Manager / Team Leader 基座；Claude Code / OpenCode / Codex / Gemini 是主要 Worker 基座。`llm` 不再作为产品主路径 Agent runtime，只保留非核心 fallback 诊断位。
- **通信协议**：Matrix 是内部协作事实源；A2A 是外部互操作协议，不是 runtimeType。本地真实 homeserver 默认是 Tuwunel，AgentHub UI 自己消费 Room timeline / participant / mention，不使用 Element Web 作为默认产品入口。当前已具备真实 Matrix account / membership / participant-token send、`/sync` 导入、mention/file 解析、mention dispatcher、可 start/stop 的 listener lifecycle，以及 `MatrixRuntimeSupervisor` 对 Manager / Worker listener 的托管。设置页已提供本地 Tuwunel 配置、启动、停止和 Matrix 诊断卡。Room participant reconcile、TaskThread room reconcile、Worker ready 和服务启动恢复会启动对应 listener；Worker stopped / stale-failed 会停掉 listener。task room 里的 `/stop` / `/cancel` 已能取消任务并释放 RuntimeLease，`/approve` / `/deny` 会作为人工控制事件进入 timeline，Matrix `m.file/m.image/m.video/m.audio` 会优先通过 media API 下载真实 `mxc://` 内容并物化到 ArtifactStore / MinIO/S3-compatible object store；下载失败时透明保留文件引用和错误原因。`tests/matrix-room-e2e.test.ts` 已用 fake Matrix homeserver 对真实 Client-Server API 形态做了协议级 e2e，验证 createRoom/register/invite/join/participant-token send/@mention 审计链路。下一步补真实 Tuwunel 现场验收、typing/presence、人工确认与 pending proposal 的强绑定、OpenClaw/QwenPaw 原生 Matrix runtime 进程化、TokenVault 和更 Matrix-sync-native 的前端投影。
- **前端事件**：AG-UI 是运行事件到前端状态的唯一收敛方向。
- **协作契约**：Spec / Contract 只描述范围、产物、验收和路径边界，不做固定模板或静态路由。
- **执行隔离**：迁移期仍有项目工作区 + `.agenthub/workdirs` + 兼容旧 `.agenthub/handoff` + local sandbox root；新内核方向是 Worker workdirs + RuntimeLease + filesystem-first ArtifactStore / SharedStorage，不把 Git 分支隔离当默认事实。
- **固定模板**：不再恢复经典团队模板、自动 Researcher/QA 注入、关键词路由、静态兜底提示词。

## 当前主路径

```text
用户在群聊发消息
  -> messages.ts 作为 ChatIngress 做鉴权、加载群聊上下文和轻量路由
  -> RoomController 确保 group room，用户消息先进入 Room timeline
  -> messages 只保留旧会话历史读取；新群聊、私聊、任务子对话不再新写 messages 投影行
  -> ManagerRuntimeService 按当前 Manager runtime 判断下一步：回复、追问、补员、派活或总结
     （OpenClaw / QwenPaw 为主；未配置时写入 runtime blocked，而不是静默回旧链路）
  -> 简单聊天：Manager / Orchestrator 直接回复
  -> 能力不足：Manager / Orchestrator 输出结构化 memberProposals，用户在主群聊卡片确认后才创建/加入真实 Agent
  -> 复杂任务：Manager-first planning action 生成团队行动方案和任务看板
  -> Manager skills 调用 Controller API 创建 run/task/task room/worker lease
  -> 每个任务创建真实 TaskThread / Matrix task room / RuntimeLease
  -> WorkerRuntime 从 Matrix task room 接单
  -> Codex / Claude Code / OpenCode / Gemini / OpenClaw Worker 执行
  -> 过程写回 Room timeline，任务契约和产物登记到 filesystem-first SharedStorage / ArtifactStore
  -> Room timeline / RunEvent / ArtifactStore 投影前端看板和子对话状态
  -> ManagerLoop 基于 Run/Task/TaskThread/Room timeline/ArtifactStore 做最终复盘并完成 run
```

## 现在已经明确的方向

1. 群聊主线是核心产品，不做固定模板壳。
2. 多 Agent 协作必须是真执行，不是 Orchestrator 假装多人。
3. AgentHub 的中期产品目标要对标 Coze，不再只当作“多 Agent 聊天工具”。
4. Contract 要做成质量门和产物链。
5. 运行过程要事件化，前端要完全收敛到 AG-UI。
6. 代码执行要保留部分产物和透明错误，不要静态兜底。
7. 未来可以接远程 A2A、Docker sandbox、trace 页面，但都不是当前内核第一优先级。

- ArtifactStore 已具备 local filesystem object-key 最小语义，前端产物卡和任务看板已经可以从 Room timeline 的 `artifact.created` replay 与 `room:timeline` realtime event 中读取 object key / storage provider / storage path；但完整 Asset Center、跨 run 资产索引和旧 snapshot/message metadata 的下线仍未完成。
- `.agenthub/shared/tasks/{taskId}` 已建立，`result.md` 已开始参与最终验收和状态同步；但 shared task directory 还要继续从“执行契约目录”升级成完整协作空间：`spec.md / plan.md / result.md / artifacts` 要贯穿分配、执行、验收、返工和下游接力，并逐步前移到 ManagerLoop 的 review 阶段。
- WorkerInstance / RuntimeLease 已经有第一轮 controller ownership：Worker ensure-ready、heartbeat、stale recovery、idle-stop、startup/shutdown lease recovery、task room running/waiting/released/stale 都已经进入 `WorkerController` / `RuntimeLeaseController`。轻量 `ControllerApi`、`ReconcileQueue` 和 `WorkerBackend` seam 已补上，但和 HiClaw Worker CRD 的差距仍包括 durable resource store、durable reconcile queue、Controller HTTP/CLI、ConfigVersionManager/hot reload、Team/Human/Manager controller、runtime reconfigure、长期 Worker 等待/恢复状态机。
- 凭证和能力控制面还比较初级。HiClaw 通过 Higress consumer 隔离真实凭证；AgentHub 近期至少要继续推进 RuntimeLease 级最小 env 注入、secret redaction、per-agent/per-task MCP scope，长期再考虑 gateway provider。
- 运行态反馈仍需要继续打磨，但关键空白点已开始收窄：群聊消息进入 CoordinatorRuntime 前会先写入 `coordinator.observing`，WorkerRuntime started 事件也会立刻推动 task/thread/lease/worker 进入 active/running/busy，并通过 Room timeline 投影到看板和 Agent tabs；WorkerRuntime 运行中 heartbeat、依赖等待/跳过、ManagerPatrol 的任务超时和 Worker 异常、Manager review started/final review 都已进入 group/task room timeline，并能投影成明确 UI 状态。下一步要把更复杂的返工/重排/模型化 review 也统一成同样连续的 Room timeline 事件。
- 子对话、进度、产物之间还需要更强的事件一致性。
- 当前 `human_interrupt` 已经能打断 active worker，把任务重新挂回 Manager 控制面，并在 group/task room timeline 中留下可见轨迹；`ManagerLoop.step()` 也已能把回到 prepared 的 task room 再次派给 WorkerRuntime。但“更复杂的多任务批量重排 / 更细粒度的局部 resume / 更强的人机接管策略”还没有完全闭环，后续要继续把这部分升级成更完整的 Manager skill 与 Worker lifecycle control。
- `OrchestratorEngine`、`TaskExecutionService`、`LocalA2ATransport`、`TaskScheduler` 已删除；剩余风险不再是旧文件本身，而是旧 snapshot/message metadata、旧 AG-UI cache 和部分 retry/replan/resume 桥接逻辑里仍可能残留 DAG-first 心智。后续应把复杂返工、重排、模型化 review、长期 Worker 等待/恢复继续收进 `ManagerLoop` / `RunController` / `WorkerRuntimeService`，并用边界测试防止旧入口复活。
- Run lifecycle 已有 start/dispatch/running/synthesizing/finish/cancel/retry/requeue/reconcile 的控制面，Controller Plane 也有了第一版 in-memory reconcile queue 和 `/api/controller/*` HTTP 面；但暂停、恢复、长期清理、trace 贯通、durable reconcile queue、稳定 Controller schema、危险操作 approval 和审计字段还需要继续补。
- 远程 A2A、MCP 能力、Skills/Rules 注入还需要更完整的产品化。
- 评估体系还不够，必须能证明多 Agent 协作为什么比单 Agent 更强。
- 群聊创建已经开始支持“群聊目标 + 轻量组队建议”；群聊内动态补员走 Orchestrator `memberProposals` + 用户确认，不走前端关键词规则。
- Space / Task Center / Asset Center / Expert Center 还没有形成统一产品壳。
