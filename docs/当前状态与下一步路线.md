# 当前状态与下一步路线

最后更新：2026-06-03

这份文档是 AgentHub 当前的“事实总览”。它的目的不是讲历史，而是让开发者和 AI Agent 先对齐现在到底在做什么、什么已经定了、什么还在推进。

## 当前一句话定位

AgentHub 当前运行时主路径是 IM 式多 Coding Agent 协作，产品北极星是 `Coze 风格的开源 AI 工作平台`。

用户在群聊里提出复杂目标，Orchestrator 动态规划任务，多个 Coding Agent 在真实子对话里执行，主群聊只展示计划、进度、产物和最终汇总。后续会在这条主路径之上继续长出 Space、Task Center、Asset Center、Expert Center 和 Eval / Trace。

底层重构方向已经明确为 HiClaw-lite Kernel：学习 HiClaw 的资源控制平面、稳定通信拓扑、Worker 生命周期和产物平面，但不直接把 Matrix / MinIO / Higress / Kubernetes 作为默认依赖。当前代码仍是过程式主链，后续要逐步把 `Run`、`Task`、`TaskThread`、`WorkerInstance`、`Artifact`、`RuntimeLease`、`RunEvent` 做成一等资源。

## 当前权威边界

- **Agent 类型**：只保留 `code-agent` 和 `llm`。A2A、MCP、Skills、Rules 都不是 Agent 类型。
- **通信协议**：A2A 是 Agent 间任务通信协议，不是 runtimeType。
- **前端事件**：AG-UI 是运行事件到前端状态的唯一收敛方向。
- **协作契约**：Spec / Contract 只描述范围、产物、验收和路径边界，不做固定模板或静态路由。
- **执行隔离**：当前主路径是项目工作区 + `.agenthub/workdirs` + `.agenthub/handoff` + local sandbox root，不把 Git 分支隔离当默认事实。
- **固定模板**：不再恢复经典团队模板、自动 Researcher/QA 注入、关键词路由、静态兜底提示词。

## 当前主路径

```text
用户在群聊发消息
  -> messages.ts 进入 Orchestrator 路由
  -> 简单聊天：Orchestrator 直接回复
  -> 能力不足：Orchestrator 输出结构化 memberProposals，用户在主群聊卡片确认后才创建/加入真实 Agent
  -> 复杂任务：动态计划 + DAG + task board
  -> 用户确认后分发
  -> 每个任务创建真实 orchestrator-task 子对话
  -> A2A message/send 作为内部任务信封
  -> LocalA2ATransport 派发到本地 runtime
  -> Codex / Claude Code / OpenCode / Gemini / LLM fallback 执行
  -> 事件写入 blackboard / execution logs / artifacts / handoff
  -> AG-UI 事件驱动前端看板和子对话状态
  -> Synthesizer 汇总最终结果
```

## 现在已经明确的方向

1. 群聊主线是核心产品，不做固定模板壳。
2. 多 Agent 协作必须是真执行，不是 Orchestrator 假装多人。
3. AgentHub 的中期产品目标要对标 Coze，不再只当作“多 Agent 聊天工具”。
4. Contract 要做成质量门和产物链。
5. 运行过程要事件化，前端要完全收敛到 AG-UI。
6. 代码执行要保留部分产物和透明错误，不要静态兜底。
7. 未来可以接远程 A2A、Docker sandbox、trace 页面，但都应在现有边界上演进。
8. 底层要从 `messages.ts -> OrchestratorEngine` 的过程式链路迁移到资源控制平面；第一刀是 RunEvent 单一 UI 真相源和 TaskThread 一等资源化。
9. 前端恢复路径已经开始改成“服务端 snapshot 优先”：`runtimeActivitySnapshot` 前推到 run detail，`TaskThread` 的 `prepared / assigned / active` 语义保留到子对话入口和 Agent tabs；同时 `agenthub.task.status` 也开始直接携带线程语义，后续继续减少浏览器本地二次拼接。
10. 后端控制面已开始真正接管 task 生命周期：`RunController` 现在除了 run lifecycle，还接住了 running-task resume requeue、blocked task 投影，以及 `executeTask()` 的 `task.assigned / task.started / task.completed / task.failed / task.cancelled` 统一落库、线程状态同步和事件广播。
11. `retry / replan` 的第一批旧散写也开始进入控制面：手动 retry、`retry_with_backoff`、`local_replan`、`agent_substitution` 的 task reset 已经改成统一走 `RunController`，让“任务回到 prepared 并等待重新执行”开始成为明确的控制面事实。
12. 动态新增任务与批量取消也开始往控制面收口：`supervisor supplement / task_split / global_replan` 的 `task.queued` 注入已经开始统一走 `RunController.queueTask()`；run 级取消现在也会同步更新对应 `TaskThread` 和子对话 metadata，而不只是改 task 表。
13. 动态任务注册入口继续收紧：`supervisor supplement / task_split / global_replan` 现在开始共用同一条“动态任务注册”路径，统一做任务资源入账、子对话关联、计划内存态同步和调度器纳管，减少 `plan.tasks.push / scheduler.addTasksToRun / 单独 executePlan` 分散散写。
14. 透明协作的第一层开始落地：任务子对话不再只剩 bootstrap、原始 prompt 和最终结果；`Manager 分派任务` 与 `Worker 接单开工` 已开始投影成可见消息，向 HiClaw 式“内部协作也像 IM 时间线一样可审计”继续靠拢。
15. 运行中的 Human-in-the-Loop 已有第一条真实链路：如果群聊已有活跃 run，用户在主群聊追加约束时，不会再默认重开 run；消息会被登记为当前 run 的 `human_interrupt`，同步写入 blackboard、run events，并由 Manager 在主群聊和活跃 TaskThread 中可见确认。
16. 这条 HITL 链路已经开始接入控制面：`RunController.reconcile()` 现在会消费未处理的 `human_interrupt`，把新约束并入未完成任务描述，登记 `manager_actions/human_interrupts/*`，并发出 `run.replanned(strategy=human_interrupt)` 与 `task.rework_requested` 事件。它还没有做到真正暂停/重启正在运行的 Worker，但已经不再只是“记录一下消息”。
17. Worker 中断链路也补上了关键基础设施：`TaskScheduler -> TaskExecutionService -> LocalA2ATransport -> runAgentReply` 的 cancel/abort 信号现在是贯通的，`cancelled` 不再被底层悄悄吞成 `failed`。Manager 处理 `human_interrupt` 时，已经会对 active task thread 执行一次真实的 live interrupt，并把对应 `runtimeLease` 标成 stale、`workerInstance` 收回到 idle。

## 当前最重要的不足

- 我们现在还更像“多 Agent 编排工作台”，还不像 Coze 那样完整的 AI 工作平台。
- 运行态反馈还不够连续，用户有时会感觉“空白”。
- 子对话、进度、产物之间还需要更强的事件一致性。
- 当前 `human_interrupt` 已经能打断 active worker，但打断后的“自动重派 / 自动重试 / 局部 resume”还没有闭环；后续要把这部分继续接到 `ManagerLoop.step()` 与 Worker lifecycle control。
- `OrchestratorEngine` 里仍有一部分动态补员/新任务计划编排、冲突合并后的后续动作，以及 progress/heartbeat 持久化没有完全收进 `RunController`。
- Run lifecycle 还不够完整，暂停、恢复、清理、trace 需要继续补。
- 远程 A2A、MCP 能力、Skills/Rules 注入还需要更完整的产品化。
- 评估体系还不够，必须能证明多 Agent 协作为什么比单 Agent 更强。
- 群聊创建已经开始支持“群聊目标 + 轻量组队建议”；群聊内动态补员走 Orchestrator `memberProposals` + 用户确认，不走前端关键词规则。
- Space / Task Center / Asset Center / Expert Center 还没有形成统一产品壳。

## 不要再当成当前事实的东西

- `workspace-agent-child`
- `classic` 工作区模板
- 固定团队和关键词路由
- `.agenthub/specs/*.spec.yml` 作为主路径
- A2A 作为 Agent 类型
- MCP / Skills / Rules 作为 runtimeType
- Git 分支隔离作为默认事实
- 静态兜底提示词或固定快速提示内容
