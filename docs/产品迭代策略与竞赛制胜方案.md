# AgentHub 产品迭代策略与竞赛制胜方案

> 基于全部文档研究、竞品分析和代码现状的综合判断。
> 目标：字节跳动 AI 全栈挑战赛 2026 获胜
> 评审标准：完成度 40% + 实用价值 30% + 创新性 30%
> 剩余时间：~9 天（至 2026-06-10）

---

## 一、核心判断

### 评审想看到什么

评审不是在选"功能最多的项目"，而是在选**"最像产品的 AI Agent 平台"**。

三个关键问题：
1. **能不能跑？** — 端到端 demo 不崩溃（完成度 40%）
2. **值不值得用？** — 解决真实开发痛点，不是玩具（实用价值 30%）
3. **有没有新东西？** — 架构创新、产品形态创新、AI Agent 范式创新（创新性 30%）

### 当前最大风险

> **不是功能不够多，而是已有功能不够稳定、不够可见。**

文档反复指出同一个结论：
- 竞品分析文档："最紧迫的不是加功能，而是修 P0 缺陷"
- 项目全景文档："最大风险不是功能不够，而是协作执行语义太多但未收敛"
- 架构分析文档："12 天到 deadline"

### 制胜公式

```
稳定可演示的 IM 协作体验
  × 多 Agent 编排的透明可视化
  × 一个"wow moment"级的创新点
  = 获胜
```

## 二、9 天作战计划

### Phase 1: 止血（第 1-2 天，6/1-6/2）

**目标：demo 不崩溃**

| 优先级 | 问题 | 修复方案 | 影响 |
|---|---|---|---|
| P0-1 | DAG 依赖失败导致死循环 | `markBlockedByFailedDependencies()` 已存在，确保调度循环正确 break | demo 不挂 |
| P0-2 | 前端自动执行计划 | 加确认步骤：计划卡片展示后，用户点击"开始执行"才 dispatch | 产品叙事完整 |
| P0-3 | 进程重启丢失运行状态 | `activeEngines` Map → DB 恢复：启动时从 `orchestrator_runs` 重建未完成运行 | demo 可靠性 |
| P0-4 | 计划生成阻塞前端 | 改为异步：立即返回 runId，前端轮询/WebSocket 获取计划 | 不超时 |

**验收标准：** 创建工作区 → @orchestrator 发任务 → 看到计划 → 确认执行 → 任务完成 → 综合报告，全流程走通不崩溃。

### Phase 2: 可见性（第 3-4 天，6/3-6/4）

**目标：让评审"看到"多 Agent 协作**

这是**完成度（40%）**和**实用价值（30%）**的核心得分点。评审看不到协作过程 = 没有协作。

### Phase 3: 创新点（第 5-7 天，6/5-6/7）

**目标：一个"评审记住你"的创新**

#### 创新点选择：Agent 主动澄清 + 用户中途介入

**为什么选这个：**

1. **竞品都没有做好。** 所有竞品（LangGraph、CrewAI、MetaGPT、Magentic-One）的 Agent 都是被动执行者——收到任务就执行，执行不了就失败。没有一个让 Agent 主动说"这个需求不清楚，我需要问你几个问题"。

2. **产品叙事完整。** IM 天然支持这个交互——Agent 在群聊里 @ 用户提问，用户回复，Agent 继续执行。这是"IM = Agent OS Shell"理念的最强体现。

3. **实现成本可控。** Clarifier 机制已部分实现（`taskClarifications` 表、澄清问题生成），只需要：
   - 把澄清问题从"计划阶段"扩展到"执行阶段"
   - 前端在群聊中渲染澄清卡片
   - 用户回答后自动恢复执行

**交互设计：**

```
群聊消息流:

[用户] 帮我实现一个支付功能

[Orchestrator] 🎯 任务编排 · 支付功能
  Phase 1: 设计    🔄 进行中
  └─ Architect · 架构设计  🔄 运行中...

[Architect] ❓ 我需要澄清几个问题：
  ┌─────────────────────────────────────────┐
  │  🤔 Architect 需要你的输入               │
  │                                          │
  │  1. 支付渠道选择？                        │
  │     ○ 支付宝  ○ 微信支付  ○ Stripe  ○ 都要│
  │                                          │
  │  2. 是否需要支持退款？                     │
  │     ○ 是  ○ 否                           │
  │                                          │
  │  3. 预计日交易量级？                       │
  │     ○ < 1000  ○ 1K-10K  ○ > 10K         │
  │                                          │
  │  [提交回答]  [跳过，用默认值]              │
  └─────────────────────────────────────────┘

[用户选择: 支付宝 + 微信, 是, 1K-10K]

[Architect] 明白了，我将基于支付宝+微信双渠道、支持退款、中等并发来设计架构。
  继续执行...

[Orchestrator] Phase 1: 设计 ✅ 完成
```

**技术实现：**
- 后端：扩展现有 `taskClarifications` 机制，Agent 执行中可通过 `blackboard.written` 或新的 `task.clarification_requested` 事件触发
- 前端：澄清卡片组件，支持选项选择和自由文本回答
- 恢复：用户回答后通过 WebSocket 推送回答到运行上下文，Agent 继续执行

#### 第二创新点（如果时间允许）：Token 成本追踪

在任务看板和编排运行页显示：
- 每个任务的 Token 消耗
- 总运行成本估算
- 各 Agent 的 Token 占比

**为什么重要：** 展示生产级意识。评审会认为"这个团队知道 AI 调用是有成本的"。

### Phase 4: 打磨（第 8-9 天，6/8-6/9）

**目标：demo 体验极致流畅**

#### 4.1 固定 Demo 脚本

推荐场景：**"让 AgentHub 给自己加一个功能"**

```
Demo 脚本（3 分钟）:

0:00 - 打开 AgentHub，展示 IM 界面（10s）
0:10 - 创建工作区，选择 AgentHub 自身项目目录（10s）
0:20 - 在群聊发送："帮我给 AgentHub 的任务看板添加一个导出 PDF 的功能"（5s）
0:25 - Orchestrator 展示计划卡片（15s）
       Phase 1: 需求分析 → Phase 2: 架构设计 → Phase 3: 编码实现 → Phase 4: 测试验证
0:40 - 用户点击"开始执行"（5s）
0:45 - 展示多 Agent 并行执行（60s）
       - Architect 设计架构 → 制品卡片
       - Builder A 编码 → 实时步骤流
       - Builder B 写测试 → 实时步骤流
       - Verifier 运行测试 → 结果卡片
       - Reviewer 代码审查 → 风险卡片
1:45 - 展示冲突解决（如果有的话）或制品汇总（20s）
2:05 - 展示 Blackboard 知识积累（20s）
       事实、决策、风险、制品引用
2:25 - 展示用户介入：回答 Architect 的澄清问题（20s）
2:45 - 展示最终综合报告（15s）
3:00 - 结束
```

#### 4.2 稳定性清单

- [ ] 重启服务后未完成运行可恢复
- [ ] Agent 执行超时不卡死（600s 超时正确触发）
- [ ] LLM API 调用失败有优雅降级
- [ ] WebSocket 断连后自动重连并恢复状态
- [ ] 并发任务不超过 3 个（Semaphore 正确工作）
- [ ] 取消操作立即生效（AbortController 传播）

#### 4.3 文档整理

- 更新 `docs/功能设计文档.md` 和 `docs/技术实现补充文档.md` 反映最终状态
- 准备 1 页产品摘要（给评审快速了解）
- 准备架构图（7 层分层 + 数据流）

## 三、制胜策略分析

### 3.1 对标评分维度

#### 完成度（40%）— 稳定压倒一切

| 得分项 | 当前状态 | 目标 |
|---|---|---|
| 端到端可演示 | 部分可走通 | 全流程不崩溃 |
| 代码质量 | 中等 | 核心路径无明显 bug |
| 架构清晰度 | 分层清晰 | 7 层架构 + 文档完备 |

**关键动作：** Phase 1 止血 + Phase 4 打磨。

#### 实用价值（30%）— 解决真实痛点

| 得分项 | 当前状态 | 目标 |
|---|---|---|
| 解决开发痛点 | 多 Agent 协作 | 可信的协作价值展示 |
| 生态集成 | 基础 | MCP/Skills 可扩展 |
| 商业模式 | 未明确 | 本地部署 + 团队协作 |

**关键动作：** Demo 场景必须是真实开发任务（不是"写一首诗"），展示多 Agent 比单 Agent 更好的证据。

#### 创新性（30%）— 评审记住你的理由

| 创新点 | 竞品状态 | AgentHub 差异化 |
|---|---|---|
| IM 作为 Agent OS Shell | 无竞品采用 | ✅ 产品形态创新 |
| Agent 主动澄清 | 竞品都是被动执行 | ✅ 交互范式创新 |
| 多 Agent 透明可视化 | AstronClaw 有基础版本 | ✅ 深度可视化 |
| A2A + AG-UI 协议 | 业界标准但少有实现 | ✅ 架构创新 |
| IM 群聊内介入 | Kimi 有基础，无开源 | ✅ 产品体验创新 |

### 3.2 竞品无法快速复制的护城河

1. **IM 群聊是天然的 Agent 交互界面。** 竞品用 dashboard/task-board，AgentHub 用聊天。聊天天然支持：
   - 实时流式输出
   - @mention 介入
   - 消息历史即执行日志
   - 多人（未来）+ 多 Agent 同时协作

2. **7 层分层架构。** 竞品通常只有 2-3 层（Agent + Tool + Storage）。AgentHub 的分层让每个层次可独立演进：
   - 产品交互层：IM + 看板
   - 编排层：DAG + Ledger
   - 协议层：A2A + AG-UI
   - 身份层：Profile + 关系
   - 执行层：多 CLI 适配
   - 能力层：Skills + Rules + MCP
   - 状态层：Blackboard + Handoff

3. **Code Agent 真实执行。** 不是模拟的"工具调用"，而是真实启动 Codex/Claude Code/OpenCode/Gemini CLI，在隔离工作目录中读写文件、执行命令。

### 3.3 评审的"加分时刻"

评审在以下时刻会额外加分：

1. **"这个产品我自己想用"** — 当 demo 展示的场景是评审自己遇到过的痛点时
2. **"这个架构想清楚了"** — 当评审看到清晰的分层、协议边界、数据流时
3. **"这个团队懂工程"** — 当看到错误处理、超时控制、状态持久化时
4. **"这个创新我没想到"** — 当 Agent 主动在群聊里 @ 用户提问时
5. **"这个 demo 很流畅"** — 当全程没有卡顿、崩溃、等待时

## 四、最关键的一个决定

> **如果只能做一件事，做什么？**

**答：把多 Agent 编排过程做成群聊内可见的结构化体验。**

原因：
- 完成度（40%）：证明多 Agent 确实在工作
- 实用价值（30%）：用户能看到每一步在做什么，知道产出是什么
- 创新性（30%）：IM 群聊内实时看多 Agent 协作，竞品没有

这就是 Phase 2 的任务进度卡片 + Agent 执行过程可见 + 制品卡片。

**没有这个，多 Agent 协作就是一个黑盒——评审无法判断它是否真的在工作，还是只是在调 LLM 生成文字。**

---

## 五、不要做的事

1. **不要加新 Agent 角色。** 8 个预设已经足够，加更多只会让 demo 更复杂。
2. **不要做 Docker 沙箱。** 本地 workdir 已经够用，Docker 增加的复杂度不值得。
3. **不要做移动端。** 桌面端 demo 就够了，移动端是加分项但不是必选项。
4. **不要做动态 Swarm。** 太复杂，demo 不稳定，评审可能看不懂。
5. **不要重构 messages.ts。** 1421 行的 God route 确实丑，但改它需要 2 天且有回归风险。
6. **不要追求 100% 测试覆盖。** 核心路径的集成测试够了，单元测试留给赛后。

## 六、赛后演进方向（供参考）

比赛结束后，以下是值得投入的长期方向：

1. **Agent 自治能力** — Agent 可以拒绝任务、请求帮助、@ 其他 Agent 协作
2. **持久化检查点** — LangGraph 风格的 DAG 节点级检查点和恢复
3. **MCP 工具生态** — 真正的 MCP 服务器接入，而不是只读工具
4. **远程 A2A 端点** — 跨机器的 Agent 协作
5. **成本优化** — Token 预算、模型降级、缓存策略
6. **团队协作** — 多人 + 多 Agent 在同一群聊中协作
7. **SOP 引擎** — MetaGPT 风格的标准化文档流
8. **插件市场** — Agent、Skill、Spec 的社区分享

## 八、一句话总结

> **不要做最多功能的项目，做最像产品的项目。**
>
> 评审的 3 分钟注意力里，只有两件事能让他们记住你：
> 1. **"多 Agent 协作真的在群聊里跑起来了，而且我能看到每一步"**
> 2. **"Agent 主动问我问题，而不是傻傻地执行错误的指令"**
>
> 把这两件事做到极致，就是获胜。
