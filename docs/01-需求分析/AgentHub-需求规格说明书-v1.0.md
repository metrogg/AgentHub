## 2. 项目概述

### 2.1 项目背景

在大模型与 AI Agent 技术快速发展的背景下，多 Agent 协作已成为提升复杂任务执行效率的关键趋势。当前主流 Agent 平台（如 Claude Code、Codex）各自独立运行，缺乏统一的协作入口和 IM 式自然交互体验。

2026 年是 Multi-Agent 协作的爆发元年，AutoGen、CrewAI、LangGraph 等框架在底层编排能力上日趋成熟，Dify、Coze 等平台在快速落地上表现突出。但**现有方案普遍存在"编排层强、交互层弱"的结构性缺陷**——多 Agent 协作仍停留在后台工作流层面，缺乏以 IM 聊天为原生形态的自然交互体验。

### 2.2 项目目标

AgentHub 旨在填补这一市场空白，打造一个 **IM 聊天式的多 Agent 协作平台**，实现以下核心目标：

1. **Agent 平台适配器层**：通过 `IAgentAdapter` 标准接口封装 Claude Code、Codex 等主流 Agent 平台的 CLI/API，向上层提供统一的 Agent 能力调用，实现一次接入、处处使用
2. **IM 聊天式交互界面**：提供类似飞书/微信的聊天体验，支持单聊、群聊、@指令协作
3. **Orchestrator 智能协调**：自动进行任务拆解与 Agent 调度，实现复杂任务的自动化分解
4. **开发者工具链闭环**：提供代码 Diff 查看、网页预览、一键部署等全流程功能
5. **多会话并行管理**：支持多 Thread 并行，每个会话独立上下文

### 2.3 项目范围

**包含范围**：
- Agent 平台适配器层（封装 Claude Code、Codex 等 Agent 平台的 CLI/API）
- IM 交互前端（Web 端聊天界面，含 IM 平台消息适配集成）
- Orchestrator 任务协调引擎
- 代码 Diff 与版本控制集成
- 网页预览与热更新
- 一键部署与环境管理
- 用户认证与权限管理

**不包含范围**：
- 自研 LLM 模型（依赖第三方 API）
- IM 平台本身的开发（仅在前端表现层做消息适配集成）
- 代码托管服务（集成 GitHub/GitLab）
- 云基础设施（依赖公有云或私有化部署）

### 2.4 产品定位

> **"IM 聊天式多 Agent 协作平台 —— 让 Agent 像同事一样在群里协同工作"**

**定位口号**："AgentHub —— 你的 AI 协作团队，就在聊天框里"

### 2.5 比赛 Demo 策略

> **目标**：字节 AI 全栈挑战赛冠军
> **原则**：Demo 优先，但每个 Demo 功能必须做到极致体验

**MVP 最小集（比赛必须交付）**：

| 模块 | 核心功能 | 为什么是必须的 |
|------|---------|---------------|
| IM 交互 | Web 端群聊界面 + @Agent 调度 + 流式输出 | 产品核心形态，评委第一眼看到的 |
| Agent 适配器 | Claude Code 或 Codex 适配器（1 个即可） | 演示 Agent 平台接入能力 |
| Orchestrator | 单轮任务拆解 + Agent 调度 | 展示多 Agent 协作核心差异 |
| 代码 Diff | 行级 Diff 展示 + 接受/拒绝 | 开发者工具链的核心价值 |
| 网页预览 | iframe 实时预览 + 手机/桌面切换 | 视觉冲击力强，演示效果好 |
| 一键部署 | 静态网站一键部署 | 全流程闭环的点睛之笔 |

**MVP 之外但能加分的功能（有时间就做）**：
- 多 Agent 群聊协作（Agent 间互相 @）
- Thread 多会话并行
- 部署回滚机制
- 更多 IM 平台适配

**争第一的关键**：
1. **演示体验流畅**：流式输出、Diff 渲染、预览加载必须丝滑
2. **一个完整闭环**：从自然语言描述需求 → 多 Agent 协作 → 代码生成 → Diff 审核 → 预览 → 部署，一气呵成
3. **视觉设计精良**：聊天界面、Diff 展示、预览效果必须好看
4. **差异化亮点突出**：IM 式多 Agent 协作是核心卖点，演示时重点展示

## 4. 市场调研与竞品分析摘要

### 4.1 竞品格局

| 框架/平台 | 开发团队 | 核心特点 | 定位 |
|-----------|----------|----------|------|
| **AutoGen** | Microsoft | Actor 模型、企业级稳定、代码执行 | 企业级多 Agent 系统 |
| **CrewAI** | 开源社区 | 角色驱动、API 简洁、LangChain 集成 | AI-as-a-team |
| **MetaGPT** | 开源社区 | SOP 引擎、软件工程优化 | 端到端软件开发 |
| **LangGraph** | LangChain | 图状态机、精确流程控制 | 复杂业务逻辑 |
| **Dify** | LangGenius | 低代码可视化、RAG 引擎 | 企业级 LLM 应用平台 |
| **Coze/扣子** | 字节跳动 | 零代码 Bot、豆包生态 | C 端与中小 B 端 |

### 4.2 核心能力对比矩阵

| 维度 | AutoGen | CrewAI | MetaGPT | LangGraph | Dify | Coze |
|------|---------|--------|---------|-----------|------|------|
| **核心范式** | 对话式协作 | 角色团队 | SOP 流水线 | 图状态机 | 可视化工作流 | 零代码 Bot |
| **学习曲线** | 中等 | 较低 | 中等 | 较高 | 低 | 极低 |
| **可视化编排** | 较弱 | 无 | 无 | 有 | 强 | 强 |
| **状态持久化** | 强 | 弱 | 弱 | 极强 | 中等 | 中等 |
| **人工介入** | 强 | 弱 | 中等 | 强 | 中等 | 弱 |
| **IM 集成** | 弱 | 弱 | 弱 | 弱 | 强（插件） | 极强（原生） |
| **开源协议** | MIT | MIT | MIT | MIT | Apache | 闭源 |

### 4.3 市场空白识别

1. **"IM 原生"的多 Agent 协作平台**：现有框架缺乏 IM 交互层，现有平台多 Agent 协作是"工作流式"而非"对话式"
2. **"@指令驱动"的 Agent 调度**：用户无法像 @同事一样显式指定 Agent 处理某事
3. **"多会话并行"的 Agent 工作区**：复杂任务需要多个独立会话同时推进
4. **"开发者优先"的全流程闭环**：代码 Diff、预览、部署在 IM 场景中几乎空白
5. **"跨 IM 平台"的统一 Agent 体验**：一套 Agent 定义，同时发布到多个 IM 平台

### 4.4 AgentHub 差异化优势

| 差异化维度 | AgentHub 设计 | 竞品现状 |
|-----------|--------------|---------|
| **原生 IM 交互** | 以 IM 群聊为首要交互场景 | 竞品以编排/工作流为核心 |
| **@Agent 调度** | 用户通过 @Agent名称 显式调用 | 竞品调度为隐式或预设工作流 |
| **多会话并行** | 单群内多 Thread 并行 | 竞品多为单会话模式 |
| **Orchestrator 协调** | 内置任务拆解协调器 | 部分有，但无 IM 层 |
| **开发者工具链** | 代码 Diff、网页预览、一键部署 | Dify/Coze 无代码能力弱 |
| **跨平台发布** | 一套 Agent 定义，多 IM 平台运行 | OpenClaw 有但 Agent 能力弱 |
| **Agent 平台适配器** | 封装 Agent CLI/API，统一 Agent 能力调用接口 | 各平台 Agent 独立接入，缺乏统一抽象 |
| **实时协作感知** | Agent 可感知群内其他成员 | 现有方案 Agent 间无"社交感知" |

#### 5.2.1 代码开发与重构（单 Agent 辅助编程）【P0】

| 要素 | 描述 |
|------|------|
| **触发条件** | 开发者需要编写新功能、修复 Bug、或重构现有代码 |
| **参与 Agent** | CodeAgent（Claude Code / Codex 适配）、ContextAgent |
| **交互流程** | 1. 用户创建单聊会话，选择 CodeAgent；2. 描述需求或粘贴代码片段；3. Agent 分析上下文，生成代码建议；4. 系统展示代码 Diff；5. 用户接受/拒绝/修改；6. 代码写入工作区 |
| **预期产出** | 可运行的代码文件、代码 Diff 记录、修改说明 |
| **成功指标** | 代码接受率 > 70%，平均响应时间 < 5 秒 |

#### 5.2.2 多 Agent 协作开发【P0】

| 要素 | 描述 |
|------|------|
| **触发条件** | 复杂功能需要前后端联动、或需要多人多角色协作完成 |
| **参与 Agent** | Orchestrator、FrontendAgent、BackendAgent、TestAgent、DocsAgent |
| **交互流程** | 1. 用户在群聊中描述完整需求；2. Orchestrator 拆解任务；3. 各 Agent 并行执行子任务；4. 中间结果在群聊中同步；5. Agent 间自动协调依赖；6. Orchestrator 汇总最终结果；7. 用户审核各模块 Diff；8. 一键部署 |
| **预期产出** | 完整功能模块（前端+后端+测试+文档）、协作过程日志 |
| **成功指标** | 复杂任务拆解准确率 > 80%，Agent 间协作无人工干预完成率 > 60% |

#### 6.9.3 MVP 不做的特别说明

以下能力在比赛 Demo 阶段明确不做，但在架构上预留扩展点：

- **多 Agent 平台故障切换**：MVP 仅接入 1 个 Agent 平台（Claude Code 或 Codex），但 `IAgentAdapter` 接口天然支持多平台注册
- **蓝绿部署/金丝雀发布**：MVP 仅支持简单的一键部署+回滚，部署流程接口预留了阶段扩展能力
- **高并发 10000+ 在线用户**：MVP 面向 Demo 场景（单用户/少数评委），架构设计上保持无状态服务可水平扩展
- **WebContainer 高级沙箱**：MVP 使用 iframe+srcdoc 方案，预览接口设计上预留了渲染引擎切换能力
- **多语言 Agent 适配器**：MVP 仅适配 1 个 Agent 平台，`PlatformType` 枚举预留了扩展空间
- **自动化 Eval 回归测试**：MVP 不做自动化测试框架，但子任务结构预留了 result 字段用于未来评估
- **Token 预算熔断系统**：MVP 仅做基础 Token 用量统计与展示，调度策略接口预留了成本控制扩展点

```
│  │/Codex)  │ │  etc.   │ │  厂商)   │ │ /MinIO) │      │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘      │
└─────────────────────────────────────────────────────────┘
```

> **架构说明**：系统包含两类适配器 —— 
> - **Agent 平台适配器**（Adapter Layer）：封装 Claude Code、Codex 等 Agent 平台的 CLI/API，位于 AgentHub 核心引擎与 Agent 平台之间，向上提供统一的 Agent 能力调用
> - **消息适配器**（表现层）：负责 IM 平台（飞书/微信/Discord/Slack）的消息格式转换，位于前端表现层，将各平台消息统一为内部格式后传递给核心引擎

### 8.2 外部依赖清单

| 依赖类型 | 依赖名称 | 用途 | 可替代方案 | 影响等级 |
|----------|----------|------|------------|----------|
| LLM 服务 | Claude API / OpenAI API | Agent 智能推理 | 本地部署模型（LLaMA 等） | 高 |
| IM 平台 | 飞书开放平台 | 消息收发 | 微信/Discord/Slack | 高 |
| 代码托管 | GitHub / GitLab | 代码存储与版本控制 | Gitee / 自建 Git | 中 |
| 云平台 | AWS / 阿里云 / 腾讯云 | 部署与基础设施 | 私有化机房 | 中 |
| 容器编排 | Kubernetes | 服务部署与扩缩容 | Docker Swarm / Nomad | 中 |
| 数据库 | PostgreSQL | 主数据存储 | MySQL / TiDB | 高 |
| 缓存 | Redis | 会话状态、热点数据缓存 | Memcached | 高 |
| 消息队列 | Kafka / RabbitMQ | 异步消息、削峰填谷 | NATS / Pulsar | 中 |
| 对象存储 | S3 / OSS / MinIO | 文件、日志、备份存储 | 本地 NAS | 低 |
| 监控 | Prometheus + Grafana | 指标采集与可视化 | Datadog / New Relic | 低 |

## 9. 风险分析

### 9.1 技术风险

| 风险编号 | 风险描述 | 影响 | 概率 | 优先级 | 应对策略 |
|----------|----------|------|------|--------|----------|
| R-TECH-01 | IM 平台 API 限制或变更 | 功能受限或中断 | 中 | 高 | 抽象适配器层，预留降级方案；关注平台变更公告 |
| R-TECH-02 | LLM API 响应延迟或不可用 | Agent 无法响应 | 中 | 高 | 引入缓存层；支持多 LLM  provider 切换 |
| R-TECH-03 | Agent 协作失控（输出质量差） | 用户体验差 | 中 | 高 | 引入 Orchestrator + 人工确认点；设置熔断机制 |
| R-TECH-04 | 上下文窗口瓶颈 | 长任务失败 | 高 | 高 | Thread 隔离 + 关键信息摘要；支持长上下文模型 |
| R-TECH-05 | 多平台适配成本高 | 进度延迟 | 中 | 中 | 先单平台验证（飞书），再渐进扩展 |
| R-TECH-06 | 代码执行安全风险 | 系统被攻击 | 低 | 高 | Docker + gVisor 多层隔离；命令黑名单；eBPF 监控 |
| R-TECH-07 | 数据一致性（多设备同步） | 消息丢失或重复 | 中 | 中 | 消息去重机制；最终一致性设计；离线缓存 |

### 9.2 业务风险

| 风险编号 | 风险描述 | 影响 | 概率 | 优先级 | 应对策略 |
|----------|----------|------|------|--------|----------|
| R-BIZ-01 | 与 Coze/Dify 直接竞争 | 资源劣势 | 高 | 高 | 聚焦"IM 原生 + 开发者工具链"差异化 |
| R-BIZ-02 | 用户接受度不及预期 | 产品失败 | 中 | 高 | MVP 快速验证；5 分钟 TTV 设计；引导式 onboarding |
| R-BIZ-03 | 企业安全合规要求 | 无法进入企业市场 | 中 | 中 | 尽早规划 SOC 2 / ISO 27001；支持私有化部署 |
| R-BIZ-04 | 开源社区生态建设缓慢 | 插件/模板不足 | 中 | 低 | 预设丰富模板；提供 SDK 和文档；举办开发者活动 |

### 9.3 运营风险

| 风险编号 | 风险描述 | 影响 | 概率 | 优先级 | 应对策略 |
|----------|----------|------|------|--------|----------|
| R-OPS-01 | 服务可用性不达标 | 用户流失 | 中 | 高 | 多可用区部署；自动故障转移；降级策略 |
| R-OPS-02 | 成本超支（LLM Token 费用） | 亏损 | 高 | 中 | Token 用量监控；缓存优化；分级套餐 |
| R-OPS-03 | 数据泄露或隐私事件 | 品牌受损 | 低 | 高 | 端到端加密；数据脱敏；定期安全审计 |
