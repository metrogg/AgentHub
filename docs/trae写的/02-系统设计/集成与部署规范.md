## 1. REST API 接口规范

### 1.1 命名约定

API 路径设计遵循 RESTful 风格，具体要求如下：

| 规则 | 说明 | 示例 |
|------|------|------|
| 资源命名 | 使用复数名词，语义清晰 | `/api/v1/sessions`、`/api/v1/messages` |
| 路径风格 | 全小写、短横线分隔（kebab-case） | `/api/v1/sessions/{session_id}/messages` |
| 版本控制 | URL 前缀 `/api/v1/`，便于后续平滑升级 | `/api/v1/sessions` |
| 嵌套资源 | 表达从属关系时使用路径嵌套，层级不超过 3 层 | `/api/v1/sessions/{session_id}/messages/{message_id}` |
| 操作命名 | 非 CRUD 操作使用动词后缀 | `/api/v1/tasks/{task_id}/cancel`、`/api/v1/deployments/{deployment_id}/rollback` |

### 1.2 请求格式

所有 REST API 请求遵循以下标准：

**Headers**

```http
Content-Type: application/json
Authorization: Bearer <jwt_token>
X-Request-ID: <uuid_v4>
```

| Header | 必填 | 说明 |
|--------|------|------|
| `Content-Type` | 是 | 固定为 `application/json` |
| `Authorization` | 是 | Bearer Token 认证，JWT 格式 |
| `X-Request-ID` | 否 | 客户端生成的请求追踪 ID，便于全链路日志关联 |

**请求体**

请求体统一使用 JSON 格式。参数校验由 Zod Schema 在网关层完成，校验失败返回 `40001` 错误码。

### 1.3 响应格式标准

**成功响应**

```json
{
  "code": 0,
  "message": "success",
  "data": { "...": "..." },
  "request_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

**错误响应**

```json
{
  "code": 40003,
  "message": "Session not found",
  "data": null,
  "request_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

**字段说明**

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | `number` | 业务状态码，`0` 表示成功，非 `0` 表示异常 |
| `message` | `string` | 人类可读的状态描述，错误时包含具体原因 |
| `data` | `object \| array \| null` | 响应数据体，成功时承载业务数据，错误时为 `null` |
| `request_id` | `string` | 请求追踪 ID，与请求头 `X-Request-ID` 对应，未传时服务端自动生成 |

### 1.4 错误码体系

错误码采用五位数字分段设计，前端可根据错误码区间做统一处理或精确匹配：

**错误码分段**

| 区间 | 含义 | 说明 |
|------|------|------|
| `0` | 成功 | 请求正常处理 |
| `40001 - 40999` | 客户端错误 | 请求参数、认证、权限、资源等问题，客户端可修正后重试 |
| `50001 - 50999` | 服务端错误 | 服务内部异常或依赖服务不可用，需运维介入 |

**详细错误码定义**

| 错误码 | 名称 | 说明 | HTTP 状态码 |
|--------|------|------|------------|
| `0` | `SUCCESS` | 成功 | 200 |
| `40001` | `INVALID_PARAMETER` | 请求参数校验失败（缺失、格式错误、类型不匹配） | 400 |
| `40002` | `UNAUTHORIZED` | 未认证或 Token 无效/过期 | 401 |
| `40003` | `NOT_FOUND` | 请求的资源不存在 | 404 |
| `40004` | `RATE_LIMITED` | 请求频率超过限制 | 429 |
| `40005` | `FORBIDDEN` | 已认证但无权限访问该资源 | 403 |
| `40006` | `CONFLICT` | 资源状态冲突（如重复创建、乐观锁冲突） | 409 |
| `40007` | `SESSION_CLOSED` | 会话已关闭，无法继续操作 | 400 |
| `40008` | `TASK_NOT_CANCELLABLE` | 任务当前状态不可取消 | 400 |
| `40009` | `DEPLOYMENT_IN_PROGRESS` | 部署正在进行中，无法重复触发 | 400 |
| `50001` | `INTERNAL_ERROR` | 服务内部未知错误 | 500 |
| `50002` | `AGENT_PLATFORM_UNAVAILABLE` | Agent 平台（Claude/Codex API）不可用 | 502 |
| `50003` | `TASK_EXECUTION_FAILED` | Agent 任务执行失败 | 500 |
| `50004` | `DATABASE_ERROR` | 数据库操作异常 | 500 |
| `50005` | `REDIS_ERROR` | 缓存/消息队列异常 | 500 |
| `50006` | `DEPLOYMENT_FAILED` | 部署流程执行失败 | 500 |
| `50007` | `GIT_OPERATION_FAILED` | Git 操作失败（clone/worktree/branch） | 500 |

### 1.5 分页标准

AgentHub 根据使用场景采用两种分页策略：

**Cursor-based 分页（消息列表场景）**

适用于数据实时追加、对一致性要求高的场景（聊天消息列表）。基于游标的偏移，不受新增数据影响。

请求参数：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `cursor` | `string` | 否 | 游标，首次请求不传 |
| `limit` | `number` | 否 | 每页条数，默认 `50`，最大 `100` |

响应格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [
      { "id": "msg_001", "content": "你好" }
    ],
    "pagination": {
      "next_cursor": "msg_050",
      "has_more": true
    }
  },
  "request_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

**Offset-based 分页（管理列表场景）**

适用于需要跳页、总数统计的管理类列表（会话列表、部署历史）。

请求参数：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `page` | `number` | 否 | 页码，从 `1` 开始，默认 `1` |
| `page_size` | `number` | 否 | 每页条数，默认 `20`，最大 `100` |

响应格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [
      { "id": "sess_001", "title": "Todo App 开发" }
    ],
    "pagination": {
      "page": 1,
      "page_size": 20,
      "total": 45,
      "total_pages": 3
    }
  },
  "request_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

## 2. WebSocket 消息协议

### 2.1 连接建立

WebSocket 连接地址：

```
ws://<host>:<port>/ws?token=<jwt_token>
```

客户端在连接建立后必须首先发送 `AUTH` 消息完成认证，服务端返回 `AUTH_SUCCESS` 后所有后续消息方可处理。未认证的连接收到非 `AUTH` 消息将被直接关闭。

### 2.2 消息类型枚举

```typescript
enum WsMessageType {
  // ==================== 客户端 → 服务端 ====================
  AUTH = 'auth',
  SEND_MESSAGE = 'send_message',
  TYPING = 'typing',
  CANCEL_TASK = 'cancel_task',
  PONG = 'pong',

  // ==================== 服务端 → 客户端 ====================
  AUTH_SUCCESS = 'auth_success',
  AUTH_ERROR = 'auth_error',
  NEW_MESSAGE = 'new_message',
  STREAM_DELTA = 'stream_delta',
  STREAM_DONE = 'stream_done',
  TOOL_CALL = 'tool_call',
  TOOL_RESULT = 'tool_result',
  TASK_UPDATE = 'task_update',
  DEPLOY_PROGRESS = 'deploy_progress',
  ERROR = 'error',
  PING = 'ping',
}
```

**消息类型说明**

| 类型 | 方向 | 说明 |
|------|------|------|
| `auth` | C → S | 客户端认证请求，携带 JWT Token |
| `send_message` | C → S | 发送聊天消息（文本、附件、@指令） |
| `typing` | C → S | 用户正在输入状态通知 |
| `cancel_task` | C → S | 取消当前正在执行的 Agent 任务 |
| `pong` | C → S | 心跳响应 |
| `auth_success` | S → C | 认证成功，携带会话信息 |
| `auth_error` | S → C | 认证失败，携带失败原因 |
| `new_message` | S → C | 推送新消息（非流式，如系统提示） |
| `stream_delta` | S → C | Agent 流式回复的增量文本块 |
| `stream_done` | S → C | 当前回合 Agent 流式回复完成 |
| `tool_call` | S → C | Agent 调用工具的通知 |
| `tool_result` | S → C | 工具执行结果 |
| `task_update` | S → C | 任务状态变更（进度、阶段切换） |
| `deploy_progress` | S → C | 部署进度更新（构建、发布、验证） |
| `error` | S → C | 通用错误通知 |
| `ping` | S → C | 心跳探测 |

### 2.3 消息格式

所有 WebSocket 消息统一使用 JSON 文本帧，结构如下：

```json
{
  "type": "send_message",
  "payload": {
    "session_id": "sess_abc123",
    "content": "@FrontendAgent 优化按钮样式",
    "mentions": ["FrontendAgent"],
    "attachments": []
  },
  "timestamp": "2026-05-14T10:30:00Z"
}
```

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `type` | `string` | 是 | 消息类型，对应 `WsMessageType` 枚举值 |
| `payload` | `object` | 是 | 消息数据体，内容因类型而异 |
| `timestamp` | `string` | 是 | ISO 8601 格式的 UTC 时间戳 |

**各类消息 Payload 定义**

```typescript
// auth
interface AuthPayload {
  token: string;
}

// send_message
interface SendMessagePayload {
  session_id: string;
  content: string;
  mentions: string[];
  attachments: Attachment[];
  reply_to_message_id?: string;
}

// stream_delta
interface StreamDeltaPayload {
  session_id: string;
  message_id: string;
  delta: string;
  agent_name: string;
}

// stream_done
interface StreamDonePayload {
  session_id: string;
  message_id: string;
  usage: {
    input_tokens: number;
    output_tokens: number;
  };
}

// tool_call
interface ToolCallPayload {
  session_id: string;
  message_id: string;
  tool_name: string;
  tool_input: Record<string, unknown>;
}

// tool_result
interface ToolResultPayload {
  session_id: string;
  message_id: string;
  tool_name: string;
  success: boolean;
  output: string;
  duration_ms: number;
}

// deploy_progress
interface DeployProgressPayload {
  session_id: string;
  deployment_id: string;
  stage: 'building' | 'deploying' | 'verifying' | 'done' | 'failed';
  progress: number;
  log: string;
}
```

### 2.4 心跳机制

保持 WebSocket 长连接的活跃性和可探测性：

| 参数 | 值 | 说明 |
|------|-----|------|
| Ping 间隔 | 30 秒 | 服务端每 30 秒发送 `PING` 消息 |
| Pong 超时 | 10 秒 | 客户端必须在 10 秒内回复 `PONG` |
| 最大重试 | 3 次 | 连续 3 次 Ping 无 Pong 响应 → 服务端主动断开连接 |
| Ping Payload | 无 | `{ "type": "ping", "payload": {}, "timestamp": "..." }` |

**心跳流程**

```
服务端                              客户端
  │                                   │
  │──── PING ──────────────────────→  │  (每 30s)
  │                                   │
  │  ←────────────────────── PONG ────│  (10s 内)
  │                                   │
```

### 2.5 重连策略

客户端断线后采用指数退避策略自动重连：

**退避参数**

| 重试次数 | 等待时间 | 累计等待 |
|----------|----------|----------|
| 第 1 次 | 1 秒 | 1 秒 |
| 第 2 次 | 2 秒 | 3 秒 |
| 第 3 次 | 4 秒 | 7 秒 |
| 第 4 次 | 8 秒 | 15 秒 |
| 第 5 次 | 16 秒 | 31 秒 |
| 第 6 次及以后 | 30 秒（上限） | — |

**重连流程**

1. WebSocket 连接断开（网络波动、服务端重启等）
2. 等待 `1s` → 尝试重连 → 失败则 `2s` → `4s` → ... → 封顶 `30s`
3. 重连成功后**自动发送 `AUTH` 消息**重新认证
4. 认证成功后发送**离线消息补拉请求**：携带本地最后一条消息的 `message_id`，通过 REST API `GET /api/v1/sessions/{session_id}/messages?after=last_message_id` 获取断线期间的消息
5. 前端合并离线消息到本地消息列表，恢复 UI 状态

### 2.6 流式消息推送

Agent 流式回复通过 WebSocket 的 `STREAM_DELTA` + `STREAM_DONE` 消息组合实现逐 token 推送。

**推送时序**

```
服务端                              客户端
  │                                   │
  │──── stream_delta ──────────────→  │  delta: "好的"
  │──── stream_delta ──────────────→  │  delta: "，我来"
  │──── stream_delta ──────────────→  │  delta: "优化"
  │──── stream_delta ──────────────→  │  delta: "按钮"
  │──── stream_delta ──────────────→  │  delta: "样式"
  │──── tool_call ─────────────────→  │  tool_name: "read_file"
  │──── tool_result ───────────────→  │  output: "文件内容..."
  │──── stream_delta ──────────────→  │  delta: "已读取"
  │──── stream_delta ──────────────→  │  delta: "样式文件"
  │──── stream_done ───────────────→  │  usage: { tokens: ... }
  │                                   │
```

**前端渲染策略**

- 每个 `STREAM_DELTA` 到达时立即追加到消息气泡尾部，实现打字机效果
- `TOOL_CALL` 和 `TOOL_RESULT` 在消息流中插入可折叠的工具调用卡片
- `STREAM_DONE` 后该轮消息状态标记为"已完成"，更新 Token 用量展示

## 3. 环境配置规范

### 3.1 环境划分

| 环境 | 标识 | 用途 | 配置来源 |
|------|------|------|----------|
| `development` | `dev` | 本地开发调试 | `.env.local` 文件 |
| `test` | `test` | 自动化测试（单元/集成/E2E） | `.env.test` 文件 / CI 环境变量 |

| `production` | `prod` | 生产环境 | Vercel Environment Variables（前端）、服务器环境变量注入（后端） |


### 3.3 密钥管理

**原则：敏感信息绝不硬编码，绝不提交版本控制。**

| 环境 | 管理方式 | 说明 |
|------|----------|------|
| 开发环境 | `.env.local` 文件 | 存放在项目根目录，已在 `.gitignore` 中排除；每位开发者自行维护 |
| 测试环境 | CI/CD Secret Variables | GitHub Actions Secrets 注入，确保测试环境与本地隔离 |
| Staging | Vercel Preview Environment Variables | 通过 Vercel Dashboard 配置，与生产环境隔离 |
| 生产环境 | 环境变量注入 | 前端：Vercel Environment Variables；后端：服务器环境变量（systemd EnvironmentFile / Docker `--env-file`） |

**敏感信息清单（严禁硬编码或提交 Git）**

- `JWT_SECRET`
- `CLAUDE_API_KEY`
- `CODEX_API_KEY`
- `VERCEL_TOKEN`
- `DATABASE_URL`（含密码）
- `REDIS_URL`（含密码）

**最佳实践**

- 定期轮换 API Key，通过环境变量无缝切换
- 生产环境 Secret 至少备份到安全的密码管理器（如 1Password Team Vault）
- `.env.local.example` 作为模板文件提交 Git（仅变量名，值为空），方便新成员快速搭建
- CI 流程中增加 Secret 扫描（如 `trufflehog`），防止密钥意外泄漏

## 4. CI/CD 流水线设计

### 4.1 流水线阶段

完整的 CI/CD 流水线按顺序执行以下阶段，任一阶段失败则终止后续执行：

```
代码提交 → Lint 检查 → 类型检查 → 单元测试 → 构建 → 部署预览 → E2E 测试 → 部署生产
```

**各阶段职责**

| 阶段 | 命令 | 说明 | 阻断策略 |
|------|------|------|----------|
| **Lint 检查** | `bun run lint` | ESLint + Prettier 代码风格校验 | 有 Error 即阻断 |
| **类型检查** | `tsc --noEmit` | TypeScript 全量类型校验 | 有类型错误即阻断 |
| **单元测试** | `bun test` | 后端单元测试 + 前端组件测试 | 有失败用例即阻断 |
| **构建** | `next build` + `bun build` | 前端构建 + 后端二进制打包 | 构建失败即阻断 |
| **部署预览** | Vercel Preview Deploy | 每个 PR 自动生成预览环境 | 部署失败通知，不阻断 |
| **E2E 测试** | `bun run test:e2e` | Playwright 端到端测试（基于预览 URL） | 有失败用例通知 |
| **部署生产** | Vercel Production Deploy | main 分支自动部署 | 需前序全部通过 |

### 4.2 Git 工作流

**分支策略**

```
main─────────────────────────────────────────────
  │
  ├── feature/CH-001-todo-app-dev────────────────
  │     │
  │     └── (开发完成后提交 PR → main)
  │
  ├── feature/CH-002-preview-sandbox─────────────
  │
  └── fix/CH-003-ws-reconnect-loop───────────────
```

| 分支类型 | 命名格式 | 用途 | 保护规则 |
|----------|----------|------|----------|
| `main` | — | 主分支，始终可部署 | 保护分支：禁止直接推送，仅通过 PR 合并；要求 Lint + TypeCheck + Test 全部通过 |
| `feature/{task-id}-{description}` | `feature/CH-001-add-auth` | 功能开发分支 | 无保护，可自由推送 |
| `fix/{task-id}-{description}` | `fix/CH-042-ws-timeout` | Bug 修复分支 | 同 feature |
| `release/{version}` | `release/v1.2.0` | 发布准备分支 | 仅从 main 切出，用于发布前的最后验证和版本号更新 |

**PR（Pull Request）要求**

1. PR 标题格式：`[task-id] 简短描述`，如 `[CH-001] 实现 Session CRUD API`
2. PR 描述必须包含：变更摘要、测试说明、关联 Issue
3. 合并前必须通过 CI 检查项：
   - ✅ Lint（ESLint + Prettier）
   - ✅ TypeCheck（tsc --noEmit）
   - ✅ Test（bun test）
4. 合并策略：Squash and Merge（将 PR 所有提交压缩为一条 commit）
5. 合并后自动删除源分支

### 4.3 自动化检测

**Lint 配置**

| 工具 | 用途 | 配置 |
|------|------|------|
| ESLint | JavaScript/TypeScript 代码规则检查 | `eslint.config.mjs`，基于 `@next/eslint-plugin-next` + 自定义规则 |
| Prettier | 代码格式化 | `.prettierrc`，单引号、无分号、2 空格缩进、100 字符换行 |

CI 命令：

```bash
bun run lint        # ESLint 检查
bun run format:check # Prettier 格式检查（CI 模式）
```

**类型检查**

```bash
tsc --noEmit        # 仅类型检查，不产出编译文件
```

**单元测试**

```bash
bun test            # Bun 原生测试运行器，执行 __tests__/ 下全部用例
```

测试覆盖率要求（渐进提升）：

| 阶段 | 行覆盖率 | 分支覆盖率 |
|------|----------|------------|
| MVP | ≥ 60% | ≥ 50% |
| Hardening | ≥ 75% | ≥ 65% |
| Production | ≥ 85% | ≥ 75% |

**构建检查**

```bash
# 前端
next build          # Next.js 生产构建（含类型检查 + 打包优化）

# 后端
bun build ./src/index.ts --outdir ./dist --target bun  # Bun 后端构建
```

### 4.4 部署流程

**前端部署（Vercel）**

AgentHub 前端通过 Vercel Git Integration 实现自动部署：

1. **Preview Deploy**（每个 PR）
   - PR 创建/更新时，Vercel 自动构建并生成唯一预览 URL
   - 预览 URL 格式：`https://agenthub-git-{branch}-{team}.vercel.app`
   - 预览环境共享 Staging 环境变量配置
   - PR 评论中自动回复预览链接

2. **Production Deploy**（main 分支合并）
   - PR 合并到 main → Vercel 自动触发 Production 构建
   - 部署到生产域名（如 `https://agenthub.app`）
   - 部署前等待 CI Pipeline 全部通过

**后端部署（单节点）**

当前 Phase 1 阶段采用单节点部署策略：

```bash
# 1. 拉取最新代码
git pull origin main

# 2. 安装依赖
bun install

# 3. 运行数据库迁移
bun run db:migrate

# 4. 构建
bun build ./src/index.ts --outdir ./dist --target bun

# 5. 重启服务（systemd / Docker）
systemctl restart agenthub
# 或
docker compose up -d --build
```

**数据库迁移**

迁移由 Drizzle ORM 管理，CI/CD 中不自动执行迁移（防止数据丢失），需要人工确认后执行：

```bash
bun run db:generate   # 生成迁移 SQL 文件
bun run db:migrate    # 执行迁移（需人工在服务器上运行）
```

**回滚策略**

| 场景 | 回滚方式 |
|------|----------|
| 前端部署回滚 | Vercel Dashboard → Deployments → 选择上一个成功的部署 → Promote to Production（即时回滚） |
| 后端部署回滚 | Docker `docker compose up -d --build` 基于上一版本 Tag 重新部署；或 systemd 回退二进制 |
| 数据库迁移回滚 | Drizzle 迁移文件记录了 `up` / `down` SQL，手动执行反向迁移 SQL |
