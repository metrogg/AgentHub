# AgentHub 使用指南

> 当前版本的核心体验是“群聊主线 + Manager-first 团队行动方案 + Room timeline / Coordinator assign / WorkerRuntime task room 任务分发 + 真实任务子对话 + `.agenthub/workdirs` 工作目录 + `.agenthub/shared/tasks` 产物交接”。如果你看到旧的 `workspace-agent-child`、固定模板或静态兜底提示词，那不是现在的主路径。
>
> 当前事实和后续路线先看 `docs/当前状态与下一步路线.md`。

## 一、环境准备

### 1. 安装 Bun
AgentHub 基于 Bun 运行时，请先安装 Bun >= 1.1.0：

```bash
# Windows (PowerShell)
powershell -c "irm bun.sh/install.ps1 | iex"

# macOS / Linux
curl -fsSL https://bun.sh/install | bash
```

### 2. 克隆项目并安装依赖

```bash
cd AgentHub
bun install
```

### 3. 配置环境变量

```bash
cp .env.example .env
```

编辑 `.env` 文件，至少配置以下项：

```env
# 可选：内部 LLM fallback（不作为 Manager 主路径）
OPENAI_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxx
# 或
ANTHROPIC_API_KEY=sk-ant-xxxxxxxxxxxxxxxx

# 可选：如果使用第三方兼容 API（如 DeepSeek、SiliconFlow）
LLM_API_KEY=sk-xxxxxxxx
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

> 服务端启动后会自动把配置写入数据库 `settings` 表，后续可通过前端界面修改。

### 4. 初始化数据库

```bash
bun run db:migrate
```

## 二、启动项目

### 开发模式（推荐）

```bash
# 同时启动服务端 + 前端
bun run dev
```

- 服务端: http://localhost:8000
- 前端: http://localhost:5173
- 自动热重载

### 体验路径

1. 先在左侧创建或打开一个群聊。
2. 在群聊里直接描述复杂任务。
3. 交给 Orchestrator 后，先看任务看板和计划；主事实源来自 Room timeline + Resource snapshot。
4. 执行时进入每个 Agent 的子对话查看真实过程。
5. 产物会在主群聊和任务看板里同步展示。

### 单独启动

```bash
# 仅服务端（带 --watch）
bun run dev:server

# 仅前端
bun run dev:web
```

### Docker 启动（可选）

```bash
docker compose up
```

## 三、基础使用流程

### 1. 单聊（Direct Session）

打开前端 http://localhost:5173，左侧栏点击 **"新建会话"**，输入消息即可与单个 Agent 对话。当前自建 Agent 默认基于 Agent Runtime / Agent Base，例如 Claude Code、OpenCode、Codex、Gemini；OpenClaw / QwenPaw 作为 Manager / Team Leader 方向。普通内部 LLM 只作为非核心 fallback。

支持的功能：
- Markdown / 代码高亮渲染
- WebSocket 流式回复，可中途取消
- 消息编辑与重新生成

### 2. 群聊（Agent Group）

#### 创建 Workspace

1. 左侧栏点击 **"新建项目"**
2. 输入项目名称和目标（如 "开发一个登录页面"）
3. 系统会自动创建一个 Workspace 和默认 Agent Group

#### 在群聊中 @Agent

在群聊中输入 `@Agent名 你的问题`，消息会路由到指定 Agent 的子会话。

#### 创建自定义 Agent

在群聊中输入：
```
创建一个 Codex 前端实现 Agent，允许读取和写入 workspace
```

系统会调用模型生成 Agent 草案卡片。自建 Agent 的含义是：选择 Codex / Claude Code / OpenCode / Gemini CLI 这类 Coding Agent 基底，再配置角色、系统提示词、skills/MCP 能力、工具权限和沙箱策略。A2A、MCP、Skills 都不是 Agent 类型。

## 四、Manager / Orchestrator 调度（核心功能）

### 触发方式

在群聊中输入：
```
@orchestrator 写一个带表单验证的登录页面
```

### 执行流程

1. **生成团队行动方案**：Manager / Orchestrator 调用模型分析目标，生成团队任务账本和任务看板，依据 Room timeline + Resource snapshot 投影结果。
2. **确认行动方案**：前端展示任务卡片，可查看任务分配。
3. **点击 Dispatch**：创建 Workspace、分配 Agent、创建 task room / RuntimeLease，并由 WorkerRuntime 执行
4. **执行中**：
   - Manager / Coordinator 通过 Room timeline 写入 `task.assigned`，WorkerRuntime 从 task room 接单
   - 各 Agent 在 `.agenthub/workdirs/{runId}/{agentName}/{taskId}` 中执行，进度、澄清、失败和产物引用写回 task room timeline
   - 失败任务透明显示错误和部分产物
   - 是否重试、返工、补员或调整分工应回到 Manager 控制面，不走静态 fallback 模板或旧内存 DAG 调度器
5. **验收与汇总**：Manager / Orchestrator 读取 Room timeline、任务结果契约和 ArtifactStore，必要时返工；最终由 Manager final review / resource-review skill 基于真实产出生成统一报告发到群聊
6. **冲突处理**：如多 Agent 修改同一文件，自动检测冲突，并交由 Manager / Orchestrator 模型决定处理方式

### Room 通信记录

每个群聊和任务子对话都会有对应 Room timeline。Manager 分派、Worker 接单、进度、澄清、失败、产物引用和最终复盘都应写入 timeline；前端再从 timeline、资源状态和 AG-UI 投影出任务看板、子对话入口和产物卡。A2A 不再作为内部主通信路径，只保留给外部互操作。

### 查看进度

任务执行过程中，可通过后端日志或数据库查看状态：

```bash
# 查看 workspace_tasks 状态
sqlite3 storage/agenthub.db "SELECT id, title, status, agent_id, attempt_count FROM workspace_tasks;"

# 查看 orchestrator_runs
sqlite3 storage/agenthub.db "SELECT id, status, summary_message_id FROM orchestrator_runs;"
```

## 五、Code Agent 配置

### 前提条件

确保本机已安装至少一个 Code Agent CLI 工具：

```bash
# Codex (OpenAI)
npm install -g @openai/codex

# Claude Code (Anthropic)
npm install -g @anthropic-ai/claude-code

# OpenCode
npm install -g @opencodeai/opencode
```

### 检测与配置

1. 前端打开 **设置 → Agent Runtimes**（旧 UI 可能仍叫代码工具），系统会自动探测本机已安装的 CLI
2. 点击对应工具的 **"配置"** 按钮，输入 API Key
3. 创建 Agent 时选择对应 Agent Runtime / Agent Base 与模型、skills、MCP 和权限组合

`a2a` 是外部互操作协议，`mcp` 与 skills 是 Agent 能力层，不要把它们配置成 Agent 类型。`llm` 不再作为产品主路径 Agent runtime。

### 专家配置的组合模型

AgentHub 里的“专家”不是一种新的 Agent runtime，而是一个可组合配置：

- **模型管理**只负责模型、Base URL、API Key 是否正确。
- **Agent Runtimes / Agent Bases** 只负责本机 Codex / Claude Code / OpenCode / Gemini CLI 以及 OpenClaw / QwenPaw 等基底是否可用，以及各自原生认证/配置是否健康。旧 UI 中的 `Coding Tools` 只是历史命名。
- **专家 Agent 配置**负责把某个 CLI 运行器、某个模型、若干 Skills/MCP 能力绑定到一个角色上。

系统还保留一个单独可见的 **内部 LLM 默认模型**，只影响欢迎页动态提示、临时诊断和非核心 fallback，不影响具体专家 Agent 的 runtime × 模型 × skills 组合，也不作为 Manager / Orchestrator 主路径。

因此同一个群聊里可以同时存在：

- Claude Code × DeepSeek × 前端 Skills
- Claude Code × Kimi × 数据分析 Skills
- OpenCode × MiMo × 文档生成 Skills

这些组合按 Agent 独立保存。沙箱启用后，每个 Agent 的执行目录、缓存、临时目录和配置目录也应彼此隔离，避免模型凭据、CLI 会话或产物串台。

### 沙箱策略

在 Agent 设置中选择沙箱级别：

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| `workspace-write` | 在 `.agenthub/workdirs/{runId}/{agentName}/{taskId}` 中写入，必要产物通过 handoff 交接 | 代码生成、重构 |
| `danger-full-access` | 同样使用任务工作目录，但允许更高权限的命令和文件操作 | 需要修改配置文件的复杂任务 |

当前 Code Agent 不再暴露 `read-only` 作为公开配置项。研究/审查语义应通过角色职责、工具权限和上下文策略表达，而不是再走旧的 code-agent 沙箱分支。

当前默认执行路径不是 Git 分支隔离，而是 `local-workdir` provider 提供的“本机进程 + Agent 独立 workdir + sandbox root + handoff”。`docker-sandbox` 是可选增强路径，只有在设置或策略中明确启用，并且 Docker Sandboxes 诊断为可运行时才会使用。

`local-workdir` 会为每个任务额外创建独立的运行时目录，并注入独立的 `TMP/TEMP/TMPDIR`、`APPDATA/LOCALAPPDATA`、`XDG_*`、npm/bun cache 路径。它的作用是减少 CLI 的配置污染和临时文件串台，但它不是 OS 级硬隔离。

如果没有选择本地项目工作区，AgentHub 会自动创建一个可写工作空间。默认位置在系统用户数据目录下，例如 Windows 的 `%LOCALAPPDATA%\AgentHub\workspaces`；也可以在 **设置 → 通用 → 默认工作空间存储路径** 修改。不要把默认工作空间设置到 AgentHub 源码目录里。

### Docker Sandboxes

Docker Sandboxes 是可选增强隔离层，不是当前默认执行路径。只有在设置或策略中显式启用，并且本机已安装且可调用 `sbx` CLI 时才会进入该路径。显式启用示例：

```env
AGENTHUB_SANDBOX_PROVIDER=docker-sandbox
```

显式启用后，AgentHub 会：

- 根据 Agent 的 `codeAgentType` 自动选择 `sbx create` 的 agent 类型
- 把 Agent 的实际执行目录作为 sandbox workspace
- 把本次任务的 temp/cache/config/home/data 目录作为额外 workspace
- 通过 `sbx exec` 在 sandbox 内运行对应 Code Agent CLI
- 超时、取消或服务退出时清理对应 sandbox

设置页中的 Docker Sandboxes 状态会拆成 `sbxInstalled / daemonReady / dockerLoggedIn / policyConfigured / sandboxRunnable / supportsPerAgentIsolation`。只有 `sandboxRunnable=true` 时，才表示 Docker Sandboxes 当前真的可运行。

注意：当前默认 provider 是 `local-workdir`。普通 Docker 容器兼容入口不再作为独立路径保留；需要更强隔离时，应通过 `docker-sandbox` provider 进入 Docker Sandboxes。

## 六、模型配置

### 前端配置（推荐）

打开前端 **设置 → 模型**，可配置：
- 模型目录
- API Key 和 Base URL
- 连接测试

打开 **设置 → 通用**，可配置：
- 内部 LLM fallback 模型

打开 **设置 → Agent Runtimes**（旧 UI 可能仍叫代码工具），可查看：
- CLI 是否安装
- 原生认证状态
- 原生配置文件状态
- Docker Sandboxes 是否 ready

打开 **Agent 配置**，才是实际选择：
- `code agent`
- `model`
- `skills / MCP`
- `sandbox`

### 环境变量配置

在 `.env` 中配置后重启服务：

```env
# OpenAI
OPENAI_API_KEY=sk-xxx

LLM_MODEL=xxx
```

## 七、常见问题

### Q: 启动后前端显示 "无法连接到服务器"

检查：
1. 服务端是否启动（`bun run dev:server`）
2. `.env` 中的 `CORS_ORIGIN` 是否包含前端地址（默认 `http://localhost:5173`）
3. 浏览器控制台是否有 CORS 错误

### Q: Agent 回复 "API Key 未配置"

检查：
1. `.env` 中是否配置了至少一个供应商的 API Key
2. 前端设置中的模型配置是否保存成功
3. 服务端日志中的 `redactSensitive` 是否脱敏了 Key（正常现象）

### Q: Code Agent 没有实际执行代码

检查：
1. Agent 是否绑定了可用的 Agent Runtime / Agent Base
2. 本机是否安装了对应的 CLI 工具（`codex` / `claude` / `opencode`）
3. `ENABLE_LOCAL_CLI_PROBES` 是否为 `true`
4. Agent 的 `sandboxPolicy` 是否为 `workspace-write` 或 `danger-full-access`
5. 设置页中 Docker Sandboxes 是否已经达到 `sandboxRunnable=true`

### Q: 为什么看不到 Git 分支隔离

当前主路径不是 Git 分支隔离，而是 `.agenthub/workdirs` + 本地 sandbox root + handoff。Git 能力只作为后续冲突分析或增强能力保留，不应作为默认执行方式排查。
