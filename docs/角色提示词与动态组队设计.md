# 角色提示词、Skill 包与动态组队设计

最后更新：2026-06-01

本文细化 AgentHub 的“角色、提示词、Skill、团队/群聊”设计。目标不是恢复固定团队模板，而是让 Orchestrator 能基于群聊目标、现有成员能力、任务风险和产物要求动态组队。

这里的“专家”就是 Agent 的产品化称呼。专家配置就是 Agent 配置，不应再做一套独立于 Agent 的专家身份、专家 runtime 或专家执行链路。

## 设计结论

1. 角色不是几句人设，而是“能力画像 + 提示词模板 + Skill 包 + 权限边界 + 输出契约”。
2. Orchestrator 也必须是一个严肃角色：它不应该写成固定 Stage 脚本，而应具备目标理解、能力缺口分析、动态组队、DAG 规划、A2A 分发、冲突处理和最终综合能力。
3. 团队可以手动组建，也可以由群聊目标驱动智能推荐。
4. 已有群聊执行新任务时，如果现有成员能力不足，Orchestrator 可以申请拉新 Agent 入群；默认需要用户确认，不能静默添加。
5. Skill 要分三层：全员通用协作 Skill、角色专属 Skill、任务自动匹配 Skill。

## Agent / 专家配置重构方向

现有 Agent 配置已经有 `systemPrompt`、`roleProfile`、`skillIds`、`toolPermissions`、`sandboxPolicy` 等字段，但配置体验还偏工程参数。建议重构为“基础配置 + 专家能力 + 运行权限 + 协作策略”四层。

### 1. 基础配置

- 名称
- 头像 / 颜色
- 简介
- 分类：技术工程、产品设计、数据智能、内容创作、质量安全、运营发布等
- 适合场景

### 2. 专家能力

- 角色背景
- 职责
- 不负责事项
- 能力标签
- 接受任务类型
- 输出契约
- 质量门
- 默认 Skill 包
- 推荐 MCP 能力

### 3. 运行权限

- runtimeType：`code-agent` 或 `llm`
- codeAgentType：Codex / Claude Code / OpenCode / Gemini
- 模型覆盖
- toolPermissions
- sandboxPolicy
- contextPolicy
- 是否需要审批

### 4. 协作策略

- 是否允许 Orchestrator 自动调用
- 适合的团队拓扑
- handoff / review / fallback 关系
- 是否可作为临时补员
- 是否可作为群聊默认 Orchestrator

建议把这些结构落到 `roleProfile` 或未来统一的 `agentProfile` schema 中，而不是散落在 prompt 文本里。

## 提示词组合模型

不要把每个 Agent 写成一段无法维护的大 prompt。建议采用以下组合：

```text
Final Agent Prompt =
  Team Common Protocol
  + Agent Role Brief
  + Role-specific Background
  + Bound Skills Context
  + Task Runtime Context
  + Output Contract
  + Safety / Permission Boundary
```

### 1. Team Common Protocol

所有群聊成员都应共享：

- 你处在 AgentHub 群聊协作中。
- 主群聊只展示计划、状态、汇报和产物；详细执行写入任务子对话。
- 所有任务来自 Orchestrator 的 A2A message/send envelope。
- 必须尊重工作目录、handoffPath、allowedPaths、sandboxPolicy。
- 输出要区分事实、推断、风险和完成项。
- 产物必须写清路径、用途、验证方式和是否可交接。
- 不要伪造其他 Agent 的产出。

### 2. Agent Role Brief

角色 brief 不是“你很专业”这种空话，而要包含：

- 背景设定：你在团队里的位置。
- 主要职责：你负责什么，不负责什么。
- 输入：你需要什么上下文。
- 输出：你必须产出什么结构。
- 质量门：你完成前必须自检什么。
- 权限边界：能不能写文件、能不能跑命令、能不能联网、是否要审批。

### 3. Skill Context

Skill 分三类：

| 类型 | 来源 | 作用 |
| --- | --- | --- |
| 全员通用 Skill | 群聊 / 工作区 | 统一协作、handoff、产物记录、状态汇报 |
| 角色专属 Skill | Agent profile | 强化某个角色能力 |
| 任务匹配 Skill | SkillRegistry 自动检索 | 补足本次任务需要的方法和工具 |

当前代码已经支持 `profile.skillIds` 作为预装技能，并通过 `buildSkillContextWithPreset()` 先加载专属工具箱，再补自动匹配技能。下一步应该把全员通用 Skill 也纳入 group/team profile。

## 全员通用 Skill 设计

建议新建这些 AgentHub 内置协作 Skill：

### collaboration-protocol

用途：

- 告诉 Agent 如何在群聊、子对话、黑板、handoff 中协作。
- 规定状态汇报和最终汇报格式。

适用：

- 所有群聊成员。

### artifact-handoff

用途：

- 规范产物如何写入 `.agenthub/handoff`。
- 说明下游只能优先读 `handoffPath`，不能猜相对路径。

适用：

- Researcher、Designer、Coder、Integrator、Writer。

### project-context

用途：

- 教 Agent 如何快速读项目结构、README、AGENTS.md、现有约定。
- 避免一上来乱改。

适用：

- 所有 Code Agent。

### status-reporting

用途：

- 规定 Agent 执行过程如何汇报：
  - 当前阶段
  - 正在做什么
  - 阻塞点
  - 已产出文件
  - 下一步

适用：

- 所有群聊成员。

### safety-boundary

用途：

- 规范危险命令、路径边界、审批点、凭据处理。

适用：

- 所有具备 shell / workspace-write 权限的成员。

### verification-contract

用途：

- 规范测试、构建、截图、预览和验收结果如何表达。

适用：

- Coder、Verifier、Reviewer、Integrator。

## 核心角色设计

### Orchestrator

背景设定：

> 你是 AgentHub 群聊的协作总指挥。你不是替所有人完成任务的单 Agent，而是负责理解目标、评估现有团队能力、动态组队、生成 DAG、通过 A2A 分发任务、监控进度、处理异常、汇总真实结果。

职责：

- 理解用户目标和群聊目标。
- 判断是否需要澄清。
- 评估当前群聊成员能力是否足够。
- 生成团队组建建议或补员申请。
- 生成动态 DAG，不用固定三段式。
- 给每个任务明确输入、输出、验收和依赖。
- 通过 A2A message/send 分发任务。
- 监控任务状态，必要时重试、改派、暂停或请求用户确认。
- 基于真实子任务结果综合，而不是凭空总结。

不应做：

- 不要因为关键词自动套固定团队。
- 不要静默拉新 Agent。
- 不要替成员伪造执行过程。
- 不要把未验证产物说成已完成。

建议预装 Skill：

- collaboration-protocol
- agent-selection
- dag-planning
- artifact-handoff
- conflict-resolution
- status-reporting
- run-lifecycle

输出契约：

```json
{
  "decision": "clarify | plan | execute | request_members | summarize",
  "reason": "为什么这么做",
  "currentTeamFit": {
    "sufficient": true,
    "missingCapabilities": []
  },
  "proposedMembers": [],
  "plan": {
    "phases": [],
    "tasks": []
  },
  "userApprovalRequired": false
}
```

### Clarifier / Product Manager

背景设定：

> 你是需求澄清和产品定义角色。你的价值不是多问问题，而是把模糊目标变成可执行边界。

建议预装 Skill：

- requirements-clarification
- acceptance-criteria
- user-story-mapping

输出：

- 目标复述
- 关键假设
- 缺失信息
- 验收标准
- 不做范围

### Researcher / Analyst

背景设定：

> 你负责收集事实、竞品、资料、技术依据和数据证据。你必须区分事实、来源、推断和不确定性。

建议预装 Skill：

- research-method
- source-evaluation
- fact-check
- artifact-handoff

输出：

- 关键发现
- 来源和可信度
- 对后续角色的建议
- 可交接素材
- 风险和空白

### Architect

背景设定：

> 你负责系统结构、技术选型、模块边界、数据流和集成策略。你不直接追求写代码，而是降低实现和维护风险。

建议预装 Skill：

- codebase-navigation
- architecture-review
- interface-design
- risk-modeling

输出：

- 架构方案
- 关键接口
- 数据模型
- 依赖和风险
- 实现约束

### Product / UX / Visual Designer

背景设定：

> 你负责把目标转成信息架构、交互流程、视觉方向、内容层级和素材需求。你要让 Builder 能直接实现。

建议预装 Skill：

- ux-flow
- visual-direction
- content-structure
- accessibility-check

输出：

- 页面结构
- 交互流程
- 文案/内容框架
- 视觉基调
- 组件和状态清单

### Coder / Builder

背景设定：

> 你是工程实现者。你要先读现有项目约定，再小步改动、真实写文件、真实验证，最后提交清晰的 diff 摘要。

建议预装 Skill：

- project-context
- frontend-engineer 或 backend-engineer
- tdd
- diagnose
- artifact-handoff

输出：

- 修改文件列表
- 关键实现说明
- 验证命令和结果
- 产物路径
- 剩余风险

### Verifier / Tester

背景设定：

> 你负责验证，不负责美化结论。你运行测试、构建、类型检查、预览检查，输出可复现结果。

建议预装 Skill：

- verification-contract
- test-runner
- playwright 或 browser-check
- screenshot-review

输出：

- 执行命令
- pass/fail
- 失败日志摘要
- 复现步骤
- 是否阻塞交付

### Reviewer / QA Reviewer

背景设定：

> 你负责审查和验收。你优先找真实问题、风险和遗漏，不做泛泛表扬。

建议预装 Skill：

- review
- security-review
- acceptance-review
- verification-contract

输出：

- 按严重程度排序的问题
- 文件/位置
- 影响
- 修复建议
- 是否可交付

### Integrator

背景设定：

> 你负责整合多个 Agent 的产物，处理冲突、连接上下游，并形成最终可交付版本。

建议预装 Skill：

- artifact-handoff
- conflict-resolution
- release-checklist
- verification-contract

输出：

- 合并策略
- 冲突处理
- 最终产物索引
- 验证状态
- 交付说明

### Writer / Editor

背景设定：

> 你负责把研究、设计或工程结果转成清晰文档。你必须保留事实依据，不夸大能力。

建议预装 Skill：

- writing-shape
- edit-article
- source-grounding
- document-formatting

输出：

- 结构化文档
- 摘要
- 引用/依据
- 待补信息

## 群聊创建设计

参考 Kimi 的“群聊名称 + 群聊目标 + 选择成员”思路，AgentHub 应支持两种创建方式。

### 方式一：手动组建群聊

适合用户已经知道要哪些 Agent。

字段：

- 群聊名称
- 群聊目标（可选）
- 工作空间
- 成员选择
- Orchestrator 选择或自动创建
- 是否允许 Orchestrator 在运行中申请补员

规则：

- 手动选择的成员直接入群。
- 群聊目标只作为长期上下文，不触发固定模板。
- 如果没有 Orchestrator，应提示必须选择或创建一个 Orchestrator。

### 方式二：目标驱动智能组队

适合用户只知道目标，不知道需要哪些 Agent。

流程：

```text
用户填写群聊名称 + 群聊目标
  -> 点击“智能推荐成员”
  -> Orchestrator/Team Builder 读取目标和可用 Agent 库
  -> 输出 teamFormationProposal
  -> 前端展示推荐成员、缺失能力、新 Agent 草案和理由
  -> 用户确认
  -> 创建群聊 + 成员 + 群聊目标
```

注意：

- 推荐不是执行模板。
- 用户可以删减成员。
- 新 Agent 草案要展示 runtime、codeAgentType、systemPrompt 摘要、skills、权限和沙箱。
- 只有用户确认后才创建新 Agent 或拉入群聊。

建议 `teamFormationProposal`：

```json
{
  "goalSummary": "群聊目标摘要",
  "recommendedTopology": "single | supervisor | parallel_research | pipeline | review_loop | grouped",
  "existingMembers": [
    {
      "agentId": "agent-id",
      "roleInTeam": "Builder",
      "reason": "为什么适合"
    }
  ],
  "newAgentDrafts": [
    {
      "name": "Fact Checker",
      "role": "事实校验",
      "runtimeType": "code-agent",
      "codeAgentType": "opencode",
      "skillIds": ["source-evaluation", "fact-check"],
      "sandboxPolicy": "read-only",
      "reason": "当前成员缺少事实校验能力"
    }
  ],
  "risks": [],
  "userApprovalRequired": true
}
```

## 群聊内动态补员

用户在已有群聊中新派任务时，可能出现“现有成员能力不够”的情况。这里应该允许 Orchestrator 申请拉新 Agent。

### 判断逻辑

Orchestrator 应先评估：

- 当前成员有哪些能力标签？
- 当前成员是否具备所需技能和权限？
- 是否有成员可通过临时加载 Skill 补足？
- 是否必须新增 Agent？
- 新 Agent 是临时加入本次 run，还是长期加入群聊？

### 补员申请

Orchestrator 不能静默新增成员。默认流程：

```text
任务进入群聊
  -> Orchestrator 做 capability gap analysis
  -> 如果缺口可由现有成员 + skill 补足，优先补 skill
  -> 如果缺口明显，发出“需要新成员”申请
  -> 用户批准
  -> 创建/拉入 Agent
  -> 新成员获得任务子对话并参与 DAG
```

补员申请卡应展示：

- 缺少什么能力
- 为什么现有成员不够
- 推荐的新 Agent 名称和职责
- 预装 skills
- 权限和沙箱策略
- 临时加入还是长期加入
- 预计参与哪些任务

### 临时成员与长期成员

建议支持两种：

| 类型 | 生命周期 | 适合场景 |
| --- | --- | --- |
| 临时成员 | 仅本次 run 有效 | 偶发能力缺口 |
| 长期成员 | 加入群聊成员列表 | 群聊目标长期需要 |

临时成员也必须有真实子对话和真实执行记录，不能只是 Orchestrator 的内部 prompt。

## 前端产品建议

### 创建群聊弹窗

建议信息结构：

- 顶部说明：Orchestrator 会根据群聊目标协助组队和分工。
- 群聊名称。
- 群聊目标：建议放宽到 200-500 字，50 字太短。
- 工作空间选择。
- 创建方式：
  - 手动选择成员
  - 根据目标智能推荐
- 成员列表：
  - 已选 Agent
  - 可选 Agent
  - 推荐新增 Agent 草案
- 高级开关：
  - 允许运行时申请补员
  - 新成员默认临时加入
  - 高风险权限需要确认

### 群聊资料页

群聊不只是 session，还应该有 team profile：

- 群聊目标
- 当前成员
- 成员职责
- 全员通用 Skill
- 允许的工作空间
- Orchestrator 策略
- 最近运行记录

### 运行中的补员卡

主群聊或任务看板里出现：

```text
Orchestrator 建议拉入 Fact Checker
原因：当前任务需要事实核验，现有成员没有 source-evaluation / fact-check 能力。
权限：read-only
Skills：source-evaluation, fact-check
加入范围：仅本次任务
[批准] [拒绝] [编辑后批准]
```

当前实现已落地一版结构化补员卡：Orchestrator 通过 `memberProposals` 输出候选专家，前端只负责展示和确认，后端只在用户确认后创建/加入真实 Agent。

## 实施路线

### Phase 1：文档和提示词体系

- 把现有 `ROLE_PRESETS.systemPrompt` 改成组合式模板。
- 新增全员通用 Skill 文档。
- 给核心角色补 `background/defaultSkillIds/outputContract`。

### Phase 2：群聊目标和智能组队

- 创建群聊 UI 增加“群聊目标”。
- 增加“手动选择 / 智能推荐”模式。
- 增加 teamFormationProposal 接口。
- 用户确认后创建群聊和成员。

### Phase 3：运行中补员

- Orchestrator plan 前加入 capability gap analysis。
- 当前成员不足时生成 `memberProposals`。
- 前端展示补员申请卡。
- 用户批准后创建临时/长期 Agent 并加入本次 DAG。

### Phase 4：Skill 闭环

- 支持 group sharedSkillIds。
- Agent profile 支持 defaultSkillIds。
- 任务执行时 prompt 组合为：group shared skills + agent default skills + auto matched skills。
- 前端展示本次任务实际加载了哪些 skills。

## 判断准则

如果一个设计符合下面几点，方向基本正确：

- 角色可以帮助 Orchestrator 决策，但不替 Orchestrator 决策。
- Skill 增强 Agent 能力，但不制造新 runtimeType。
- 群聊目标影响团队推荐，但不变成固定模板。
- 新 Agent 入群必须可见、可解释、可拒绝。
- 每个新成员都必须有真实任务子对话和真实产物记录。
