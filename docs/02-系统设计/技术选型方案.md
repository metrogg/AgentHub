## 1. 选型背景与原则

### 1.1 项目背景

AgentHub 是一个 IM 聊天式的多 Agent 协作平台，采用六层分层架构（表现层 → 网关层 → 编排层 → Harness 层 → 适配器层 → 基础设施层）。核心场景包括：实时流式 IM 对话、多 Agent 并行任务调度、代码 Diff 可视化、Web 预览沙箱、一键部署流水线。

### 1.2 比赛约束

| 约束项 | 说明 |
|--------|------|
| 团队规模 | 单人 / 小团队开发 |
| 迭代节奏 | 快速迭代，Demo 展示优先 |
| 时间窗口 | 比赛周期内完成 MVP 到可演示状态 |
| 资源限制 | 无专用运维，需低运维开销的技术栈 |

### 1.3 选型原则

1. **善用开源、最小依赖** — 优先使用平台原生能力，避免引入重量级框架后又被其约束
2. **快速原型能力** — 技术栈应支持"写少跑快"的开发体验，Demo 阶段时间成本是第一成本
3. **渐进演进** — MVP 阶段简单直接，但架构预留后续扩展接口，不做"一次性原型"
4. **控制力优先** — 对核心差异化能力（Agent Loop、上下文压缩、工具治理）保持代码级控制
5. **安全保守默认** — 所有工具/服务默认 Fail-Closed，不配置不等于不安全

## 2. 前端技术栈对比选型

### 2.1 候选方案

| 方案 | 核心特征 |
|------|----------|
| **A: Next.js App Router** | React 生态、SSR/SSG、文件路由、Server Actions、API Routes、Vercel 一键部署 |
| **B: Vite + React (SPA)** | 极简配置、亚秒级 HMR、纯前端 SPA、Rollup 打包 |
| **C: 纯 HTML/JS** | 零框架依赖、直接部署、无构建步骤 |

### 2.2 多维度评估

| 评估维度 | A: Next.js App Router | B: Vite + React SPA | C: 纯 HTML/JS |
|----------|----------------------|---------------------|---------------|
| **IM 聊天 UI 实现难度** | 🟢 低 — React 组件生态丰富，支持虚拟滚动（react-virtuoso）、Markdown 渲染（react-markdown）直接集成 | 🟢 低 — 同 React 生态，但需自行处理路由和状态管理基础设施 | 🔴 高 — 需手写消息渲染、滚动优化、状态管理，DOM 操作繁琐 |
| **流式消息渲染支持** | 🟢 优 — Server Actions + Streaming 原生支持，React Suspense 可优雅处理流式数据的增量渲染；也可客户端 fetch + ReadableStream 消费 SSE | 🟡 中 — 需手动实现 SSE/WS 消费 + 状态更新，但 React 的 `useOptimistic` 可辅助流式 UI | 🔴 差 — 需手写 DOM 增量更新、字符级追加、光标位置管理 |
| **WebSocket 集成** | 🟢 优 — 可在 Client Component 中使用原生 WebSocket API，也可通过 Server Actions 桥接；Next.js 中间件层可做 WS 升级认证 | 🟢 优 — 直接使用浏览器 WebSocket API，无额外限制 | 🟡 中 — 原生 WebSocket API 可用，但缺少状态同步机制 |
| **代码 Diff 组件库** | 🟢 优 — Monaco Editor（@monaco-editor/react）深度集成 React，支持 DiffEditor 模式、语法高亮、行内对比；也可选轻量的 react-diff-viewer | 🟢 优 — 同 A 方案，Monaco Editor 对 React 有官方封装 | 🔴 差 — Monaco Editor 需模块加载器，纯 HTML 集成极其困难；只能用简易 diff 展示 |
| **iframe 沙箱支持** | 🟢 优 — React 组件封装 iframe + srcdoc，可通过 postMessage + useRef 安全通信；Server Component 可预渲染沙箱模板 | 🟢 优 — 同 React 组件模式，实现方式一致 | 🟡 中 — 原生 DOM 操作可行，但缺乏响应式状态同步 |
| **部署便利性** | 🟢 优 — `next build && next start` 一条命令；Vercel 零配置部署；也支持 Docker、Node.js 服务器、静态导出 | 🟢 优 — `vite build` 产出纯静态文件，可部署到任何 CDN/静态托管 | 🟢 优 — 零构建，直接托管静态文件 |
| **团队学习成本** | 🟡 中 — React 18/19 知识 + Next.js App Router 范式（RSC、Server Actions）；团队已具备 React 基础 | 🟢 低 — 纯 React SPA，学习曲线最平缓 | 🟢 低 — 无框架学习成本，但对开发者的工程素养要求更高 |

### 2.3 推荐选择：Next.js App Router

#### 推荐理由

**1. 流式渲染是 AgentHub 的刚需，而非可选项**

AgentHub 的核心体验是 Agent 流式回复——用户发送消息后，Agent 的回复像打字机一样逐字出现在聊天框中。Next.js App Router 的 **React Server Components + Streaming** 和 **Server Actions** 为流式响应提供了框架级支持：

- Server Action 中直接返回 `ReadableStream`，React 通过 `use()` hook 或 `<Suspense>` 渐进渲染
- 不需要额外引入 SSE 中间件或手动管理 EventSource 生命周期
- 流式渲染与 React 的 Concurrent Features 深度集成，避免阻塞主线程

相比之下，Vite SPA 需要手动实现 SSE 消费者、手动管理状态更新队列，纯 HTML 方案则需要手写 DOM 增量更新——两者在流式这种高频增量更新的场景下都缺乏框架级优化。

**2. Server Actions 简化 API 层**

AgentHub 的 REST API 端点数量有限（会话 CRUD、消息管理、部署触发，约 12 个端点），使用 Next.js Server Actions 可以将 API 逻辑与前端组件放在同一个项目中，避免额外的 API 服务部署。对于比赛 Demo 阶段（单节点部署），这极大降低了运维复杂度。

**3. 渐进式架构兼容性**

Next.js 同时支持 SSR、SSG、ISR 和纯客户端渲染。AgentHub 的会话列表页面可以利用 SSR 做首屏快速加载，聊天界面则完全客户端渲染以保持交互流畅。未来如果需要 SEO（文档型页面），无需架构变更。

**4. Monaco Editor 集成零摩擦**

代码 Diff 是 AgentHub 的差异化功能之一。`@monaco-editor/react` 为 Next.js/React 提供了一流的集成体验，包括 Web Worker 隔离（避免语法高亮阻塞主线程）、DiffEditor 三路合并模式、自定义颜色主题。选择 Next.js 意味着这条技术路径是"开箱即用"的。

**5. 部署为比赛 Demo 优化**

Vercel 对 Next.js 有一键部署支持，比赛现场演示时不需要手动配置服务器、nginx 反向代理、SSL 证书。`next build` 产出即可部署，也可通过 Docker 容器化部署到任何环境。

### 2.4 放弃方案的理由

- **Vite + React SPA**：虽然开发体验优秀，但缺少框架级流式渲染支持、需要自行搭建 API 服务、缺乏 Server Actions 带来的前后端一体化便利。对于 AgentHub 这种"前端 UI + 后端逻辑强耦合"的项目，SPA 架构需要维护两套独立服务，增加比赛阶段不必要的复杂度。
- **纯 HTML/JS**：舍弃框架便利性换来的"零依赖"不适用于 AgentHub——Monaco Editor、流式渲染、虚拟滚动等复杂 UI 组件在没有框架的情况下开发成本呈指数级增长，比赛时间窗口内不可行。

## 3. 后端运行时对比选型

### 3.1 候选方案

| 方案 | 核心特征 |
|------|----------|
| **A: Bun** | 极速启动（~12ms）、原生 TypeScript、内置 bundler/transpiler、内置 WebSocket 服务器、兼容 Node.js 生态、原生 SQLite |
| **B: Node.js + Fastify** | 成熟 NPM 生态（200 万+ 包）、Fastify 插件体系、Worker Threads 并发、长期 LTS 支持 |
| **C: Go** | 编译型语言极致性能、goroutine 原生并发、静态类型编译期安全保障、单二进制部署 |

### 3.2 多维度评估

| 评估维度 | A: Bun | B: Node.js + Fastify | C: Go |
|----------|--------|----------------------|-------|
| **启动速度（CLI 场景关键）** | 🟢 极快 — 运行时启动 ~12ms，冷启动到处理请求 < 50ms；`bun run` 瞬间执行 | 🟡 中 — Node.js 启动 ~150ms，Fastify 初始化 ~50ms，总计 ~200ms+ | 🟢 极快 — 编译后二进制启动 < 5ms，但编译步骤本身耗时 |
| **TypeScript 支持** | 🟢 原生 — 零配置运行 `.ts` 文件，内置 transpiler，不需要 ts-node 或 tsx | 🟡 需配置 — 需 tsx/ts-node 或预编译为 JS；Fastify 有 TypeScript 类型支持但需额外配置 | 🔴 不适用 — Go 是静态类型语言，但生态与 TypeScript 完全不同 |
| **Agent 平台 CLI 调用（spawn 子进程）** | 🟢 优 — `Bun.spawn()` 提供比 Node.js `child_process` 更简洁的 API，内置 streaming stdin/stdout/stderr，支持 `AbortSignal` 取消 | 🟢 优 — `child_process.spawn()` 成熟稳定，但 API 偏底层，流处理需额外 pipe | 🟡 中 — `os/exec` 可用，但 Go 的 goroutine 模型与 Node 风格子进程管理差异大 |
| **WebSocket 性能** | 🟢 极优 — 内置 `Bun.serve()` 直接支持 WebSocket，零额外依赖；单机可承载 10 万+ 并发 WS 连接，每连接开销 ~4KB 内存 | 🟡 中 — 需引入 `@fastify/websocket` 或 `ws` 库；Fastify WebSocket 性能优秀但不原生 | 🟢 极优 — gorilla/websocket 或 nhooyr.io/websocket，goroutine 每连接开销 ~2KB |
| **开发效率** | 🟢 极高 — 前后端同语言（TypeScript），共享类型定义和工具函数；`bun --hot` 热重载；内置测试运行器 | 🟢 高 — JS/TS 生态成熟，Fastify 插件化开发体验好，但需要更多样板代码 | 🔴 低 — 前后端语言不统一，需要维护两套类型定义；Go 的 error handling 和 interface 设计理念与 TS 差异大 |
| **生态成熟度** | 🟡 中 — Bun 1.x 已稳定，兼容大部分 Node.js 包，`pg`、`ioredis`、`zod` 等核心包已验证兼容；但部分边缘 npm 包可能不兼容 | 🟢 极高 — 200 万+ npm 包，所有 Agent 平台 SDK（Anthropic、OpenAI）均提供 Node.js 客户端 | 🟢 高 — Go 标准库完善，但 AI/LLM SDK 生态弱于 Node.js（Anthropic Go SDK 不如 Node.js 版本成熟） |

### 3.3 推荐选择：Bun

#### 推荐理由

**1. 比赛场景的"时间窗口"决定技术成本结构**

对于单人/小团队在比赛周期内完成 MVP，最大的风险不是"性能不够"而是"时间不够"。Bun 在三个维度上节省了大量时间：

- **零配置 TypeScript**：`.ts` 文件直接运行，不需要 `tsconfig.json` 构建配置、不需要 `tsx` 启动器、不需要 `tsc --watch` 编译。这一切节省的不只是配置时间，更是每次修改代码后的"编辑→构建→重启→验证"循环中的等待时间。
- **内置能力替代依赖**：Bun 内置了 WebSocket 服务器（不需要 `ws` 或 `@fastify/websocket`）、文件系统 API（Bun.file() 更简洁）、SQLite（不需要 better-sqlite3）、密码哈希（Bun.password）、`.env` 加载。每减少一个 npm 依赖，就减少一个潜在的兼容性问题。
- **启动速度节省调试时间**：AgentHub 的 Harness 层需要频繁调用 Agent 平台 CLI（`Bun.spawn`），每次子进程启动的延迟会累积到整体的 Agent Loop 迭代延迟中。Bun 的 spawn 速度显著快于 Node.js。

**2. WebSocket 原生内置，与 AgentHub 架构完美匹配**

AgentHub 的网关层核心是 WebSocket 网关（实时 IM 消息推送）和 HTTP REST API。Bun 的 `Bun.serve()` 同时提供 HTTP 和 WebSocket 服务，不需要额外引入任何 WebSocket 库：

```typescript
Bun.serve({
  port: 3000,
  fetch(req, server) {
    if (server.upgrade(req)) return; // WebSocket 升级
    return new Response("OK");        // HTTP 处理
  },
  websocket: {
    message(ws, message) { /* ... */ },
    open(ws) { /* ... */ },
    close(ws) { /* ... */ },
  },
});
```

这个 API 设计意味着 AgentHub 的单节点部署架构下，一个 Bun 进程即可承载 HTTP + WebSocket + 业务逻辑，不需要 Nginx 做 WS 反向代理、不需要独立 WS 服务、不需要微服务通信开销。

**3. 前后端同语言（TypeScript）的价值被低估**

在 AgentHub 中，前端（Next.js）和后端（Bun）都使用 TypeScript，这意味着：

- **共享类型定义**：`IAgentAdapter`、`UnifiedMessage`、`WsMessage` 等接口定义可以放在 `packages/shared` 中，前后端共享，编译期保证协议一致性。这在 Go 后端方案中需要手动维护两套类型或使用 OpenAPI 代码生成，都有额外成本。
- **共享工具函数**：消息序列化/反序列化、Token 估算、Diff 解析等逻辑可复用。
- **统一心智模型**：单人开发时不需要在 JS event loop 和 Go goroutine 两种并发模型之间切换。

**4. Bun 的 Node.js 兼容性已足够支撑 AgentHub 的依赖图谱**

AgentHub 后端的主要依赖清单：

| 依赖 | 用途 | Bun 兼容性 |
|------|------|------------|
| `pg` / `drizzle-orm` | 数据库驱动 | ✅ 已验证兼容 |
| `ioredis` | Redis 客户端 | ✅ 已验证兼容 |
| `zod` | Schema 校验 | ✅ 已验证兼容 |
| `jose` | JWT 签名/验证 | ✅ 已验证兼容 |
| `simple-git` | Git 操作 | ✅ 已验证兼容（基于 child_process） |
| `@anthropic-ai/sdk` | Claude API | ✅ 已验证兼容 |
| `openai` | OpenAI/Codex API | ✅ 已验证兼容 |

这些核心依赖均在 Bun 上验证兼容，AgentHub 未使用任何已知不兼容的边缘 npm 包。

### 3.4 放弃方案的理由

- **Node.js + Fastify**：生态系统最成熟，但相较于 Bun 没有显著优势。AgentHub 不需要 200 万+ npm 包的生态长尾——核心依赖只有约 10 个。Fastify 的插件体系对于 AgentHub 这种"单体应用"来说是额外的心智负担。选择 Node.js 意味着放弃 Bun 的启动速度优势和原生 TypeScript 支持。
- **Go**：性能最优，但 AgentHub 的瓶颈不在运行时性能而在 LLM API 延迟（200ms ~ 2s）。用 Go 的极致性能去优化 0.1ms 的请求路由对端到端延迟几乎没有影响。更关键的是，Go 的 AI/LLM SDK 生态不如 TypeScript 成熟（如 `@anthropic-ai/sdk` 的 Go 版本功能落后于 Node.js 版本），前后端语言不统一增加类型维护成本，单人开发时需要频繁进行思维上下文切换。

## 4. 数据库方案对比选型

### 4.1 候选方案

| 方案 | 核心特征 |
|------|----------|
| **A: PostgreSQL + pgvector** | 关系型数据库 + 向量检索扩展、ACID 事务、丰富索引类型（B-tree / GIN / GiST / IVFFlat）、成熟 ORM 支持 |
| **B: SQLite** | 零配置、嵌入式、单文件数据库、无需独立进程、适合本地开发和小规模部署 |
| **C: MongoDB** | 文档型 NoSQL、灵活 Schema、内嵌文档、水平扩展（Sharding） |

### 4.2 多维度评估

| 评估维度 | A: PostgreSQL + pgvector | B: SQLite | C: MongoDB |
|----------|--------------------------|-----------|------------|
| **消息持久化需求** | 🟢 优 — 消息表适合关系模型（id / session_id / user_id / role / content / type / created_at），支持复杂查询（按会话分页、全文搜索、时间范围过滤） | 🟡 中 — SQL 查询能力与 PG 相同，但并发写入性能受限（单写锁） | 🟡 中 — 文档模型天然适合消息存储（嵌套回复链），但跨文档关联查询（如"某用户的所有消息"）需 aggregation pipeline，复杂度高 |
| **Session 状态存储** | 🟢 优 — JSONB 列可存灵活状态，同时保持 Schema 约束；关联查询简单（session JOIN messages） | 🟡 中 — 功能足够，但 WAL 模式下高并发写入仍有瓶颈 | 🟢 优 — 文档内嵌子文档，Session+Messages 可放在同一文档中，读取一次 IO |
| **Agent 记忆存储（向量检索）** | 🟢 极优 — pgvector 提供 IVFFlat / HNSW 索引，支持 L2 / 内积 / 余弦距离，与关系数据在同一事务中查询；`WHERE ... ORDER BY embedding <=> $1 LIMIT 10` 单次查询即可完成"检索相关记忆+过滤元数据" | 🔴 差 — 无原生向量检索能力，需额外引入 sqlite-vss 扩展（社区维护，成熟度不足） | 🔴 差 — MongoDB Atlas Vector Search 仅在云托管版本可用，自托管需要额外部署向量数据库 |
| **并发支持** | 🟢 优 — MVCC 多版本并发控制，读写互不阻塞；连接池管理成熟（pgbouncer / 应用层连接池） | 🟡 中 — 单写锁（WAL 模式缓解但未完全消除），高并发写入场景（10+ 并发 Agent 同时写消息）可能成为瓶颈 | 🟢 优 — WiredTiger 存储引擎支持文档级锁，写入并发优于 SQLite |
| **部署复杂度** | 🟡 中 — 需要独立进程运行，端口配置，初始建库；但 Docker 一键部署（`docker run -e POSTGRES_PASSWORD=... pgvector/pgvector:pg16`）已大幅简化 | 🟢 极低 — 零部署，Bun 内置 `bun:sqlite` 直接使用，无独立进程 | 🟡 中 — 需要独立进程，数据目录管理 |
| **ORM 支持** | 🟢 极优 — Drizzle ORM 对 PostgreSQL 的支持最为完善（生成类型、迁移、JOIN、JSONB、pgvector 扩展）；Prisma 也完整支持 PG | 🟢 优 — Drizzle ORM / Prisma 均支持 SQLite（但部分 PG 高级特性不可用） | 🟡 中 — Prisma 支持 MongoDB 但功能受限（无 JOIN、事务模型不同）；Drizzle 不支持 MongoDB |
| **agent_post** 表（产出物存储） | 🟢 优 — JSONB 存储 Agent 产出的结构化数据（代码块、文件列表、diff 结果），支持 GIN 索引加速 JSON 内字段查询 | 🟢 优 — SQLite 3.45+ 支持 JSONB 二进制 JSON 存储 | 🟢 优 — 天然 JSON/BSON 文档存储 |

### 4.3 推荐选择：PostgreSQL + pgvector

#### 推荐理由

**1. "一个数据库解决两个核心问题"是比赛阶段的最优架构策略**

AgentHub 有两个截然不同的存储需求：结构化业务数据（用户、会话、消息、部署记录）和向量化 Agent 记忆（Long-term Memory 检索）。PostgreSQL + pgvector 在一个数据库实例中同时满足这两个需求：

- 不需要额外部署独立的向量数据库（如 Pinecone、Milvus、Weaviate）
- 业务数据和向量数据在同一事务中查询，避免分布式事务的复杂性
- `SELECT * FROM memories WHERE session_id = $1 ORDER BY embedding <=> $2 LIMIT 5` —— 向量相似度搜索和历史过滤在一次 SQL 查询中完成

这意味着比赛阶段只需要一个 `docker run pgvector/pgvector:pg16` 命令就能启动完整的数据层。

**2. pgvector 在 2025-2026 年已达到生产级成熟度**

pgvector 0.7.x 版本的关键能力：
- **HNSW 索引**：比 IVFFlat 快 10-100 倍的近似最近邻搜索，支持实时更新（无需重建索引）
- **半精度（halfvec）**：向量存储空间减半，对 AgentHub 的 embedding 维度（通常 1536 或 3072）可节省 50% 存储和内存
- **稀疏向量（sparsevec）**：支持混合检索（稀疏+稠密向量），为后续的 BM25 + embedding 混合搜索预留空间
- **标量量化索引**：进一步压缩索引大小，适合内存受限的比赛环境

**3. Drizzle ORM + PostgreSQL 是 TypeScript 生态的最佳类型安全组合**

AgentHub 选择 Drizzle ORM 而非 Prisma，理由如下：

| 对比维度 | Drizzle ORM | Prisma |
|----------|-------------|--------|
| 类型推导 | ✅ 100% TypeScript 类型推导，无需代码生成 | ⚠️ `prisma generate` 需每次 Schema 变更后手动运行 |
| Bundle 体积 | ~100KB | ~4MB+（含 engine） |
| SQL-like 查询 | ✅ `db.select().from(messages).where(eq(...))` 接近 SQL 思维 | ⚠️ Prisma Client 有自己的查询语法，学习曲线 |
| pgvector 支持 | ✅ 原生支持 `sql<...>` 模板 + pgvector 操作符 | ⚠️ 需通过 `$queryRaw` 或社区扩展 |
| 迁移 | ✅ 生成 SQL 文件，可审查和手动修改 | ✅ 生成 SQL 文件，成熟稳定 |
| Bun 兼容性 | ✅ 官方支持 | ⚠️ 需额外配置 |

Drizzle 的 `sql` 模板字面量允许直接写原生 SQL，这在 pgvector 的向量检索场景中非常关键——不需要等待 ORM 封装新特性，可以随时使用 `cosineDistance(embeddings.vector, userQuery)` 等底层函数。

**4. AgentHub 的数据模型天然适合关系型**

AgentHub 的核心数据实体及其关系：

```
User ──< Session ──< Message ──< ContentBlock
Session ──< TaskPlan ──< TaskStep
Session ──< DiffRecord
Session ──< Deployment
Agent ──< AgentCapability
Memory (session_id → embedding → metadata)
```

这些实体之间存在明确的 `1:N` 外键关系（如一个 Session 包含多条 Message，一个 Message 包含多个 ContentBlock），关系型数据库的 JOIN 查询比 MongoDB 的 `$lookup` aggregation 更直观、性能更好、类型更安全。

### 4.4 放弃方案的理由

- **SQLite**：最大的吸引力是"零部署"，Bun 内置 `bun:sqlite` 可以直接使用。但 AgentHub 的核心差异化能力——Agent 的 Long-term Memory 向量检索——SQLite 无法原生支持。引入 `sqlite-vss` 扩展意味着依赖一个社区维护的 C++ 扩展，在 Bun 运行时中的兼容性未知。且 SQLite 的并发写入瓶颈在 10+ Agent 同时产出消息时会暴露。
- **MongoDB**：文档模型对"消息"这种自包含的数据结构很友好，但 AgentHub 更多是关系型查询（"某会话的所有消息"、"某用户的所有会话"、"某 Agent 产出的所有 Diff"），这些查询在 MongoDB 中需要复杂的 aggregation pipeline。MongoDB Atlas Vector Search 需要云托管，自托管需要额外部署向量数据库。对于比赛阶段，MongoDB + 独立向量数据库的运维开销不可接受。

## 5. Agent 框架策略

### 5.1 候选方案

| 方案 | 核心特征 |
|------|----------|
| **A: 自研轻量 Harness** | 参考 Claude Code 开源架构，AsyncGenerator 驱动的 Agent Loop、buildTool 工厂模式 Tool Registry、四级上下文压缩管道、Token Budget 熔断 |
| **B: LangGraph** | Google/LangChain 生态、状态图（StateGraph）驱动的 Agent 编排、Checkpoint 持久化、Human-in-the-Loop |
| **C: CrewAI** | 角色化多 Agent 团队、基于 Crew + Task + Process 的声明式编排、快速原型开发 |

### 5.2 多维度评估

| 评估维度 | A: 自研轻量 Harness | B: LangGraph | C: CrewAI |
|----------|---------------------|--------------|-----------|
| **Agent 精细控制力** | 🟢 极高 — 16 步 AsyncGenerator Agent Loop 对每一步有完全控制权（预取、预算、压缩、API 调用、工具执行、Hooks、中断、过渡），可以在任意步骤插入自定义逻辑 | 🟡 中 — StateGraph 提供了节点和边的抽象，但对节点内部行为（如 LLM 调用的 context window 管理、工具结果的 token 消耗计算）控制力有限 | 🔴 低 — 高层抽象（Crew/Task/Process），对 Agent 内部执行细节（prompt 构建、工具调用时序、token 计数）几乎没有控制入口 |
| **上下文压缩自由度** | 🟢 极高 — 四级压缩管道（Snip→Micro→Collapse→Auto）完全自研，每级的触发条件、压缩策略、是否调用 API 都可由 Harness 精确控制；可以根据 AgentHub 的业务场景定制压缩策略 | 🔴 低 — LangGraph 的 context 管理依赖 LangChain 的 MessageHistory，压缩策略固定（滑动窗口 / 摘要），无法在"零 API 调用裁剪"和"LLM 摘要"之间做精细切换 | 🔴 低 — CrewAI 的上下文管理完全黑盒，开发者无法介入压缩策略 |
| **工具治理能力** | 🟢 极高 — `buildTool` 工厂模式要求每件工具登记九项元信息（名称、描述、参数 Schema、风险等级、并发安全标记、只读标记、权限角色等）；所有工具默认 Fail-Closed；五层纵深防御（Deny Rules → Tool Permissions → Generic Rules → Permission Mode → Auto Classifier） | 🟡 中 — LangGraph 的 ToolNode 支持工具调用，但权限模型需要在 graph 层面手动实现，框架不提供内置的工具治理机制 | 🔴 低 — CrewAI 工具装饰器非常简洁但缺乏治理层级，工具安全完全依赖开发者自律 |
| **与 Claude Code/Codex 的集成方式** | 🟢 优 — 自研的 `IAgentAdapter` 接口是 AgentHub 架构的一等公民，Harness 层通过统一消息格式与适配器层通信；Claude Code CLI 通过 `Bun.spawn` 子进程调用，Codex 通过 OpenAI API / CLI 调用；不依赖任何第三方 Agent 框架的"Wrapper" | 🟡 中 — LangGraph 可以通过自定义 Tool 包装 Claude Code CLI，但这不是框架设计的原生路径；框架的"Agent"概念与 Claude Code 的"CLI Agent"概念存在语义冲突 | 🔴 差 — CrewAI 的 Agent 是 LlamaIndex/OpenAI 生态的概念，无法直接接入 Claude Code CLI 作为独立 Agent 执行单元 |
| **比赛 Demo 定制化需求** | 🟢 极高 — 比赛 Demo 需要精确控制 Agent 的行为展示（如流式输出到 IM 界面、Diff 生成时机、工具调用的可视化），自研方案可以在 Agent Loop 的每个 yield 点插入 Demo 友好的行为 | 🟡 中 — LangGraph 的 streaming 模式可以逐节点产出，但对产出格式的精细控制不如自研 AsyncGenerator | 🔴 低 — CrewAI 对输出格式的控制粒度太粗，不适合需要"逐 token 展示"、"工具调用步骤可视化"的 Demo 场景 |
| **代码量与维护成本** | 🟡 中 — 需要从零实现 Agent Loop、Tool Registry、压缩管道，预计 Harness 层核心代码约 2000-3000 行 TypeScript；但参考 Claude Code 开源架构可以复用设计模式 | 🟢 低 — 框架提供大量开箱即用能力，代码量少 | 🟢 低 — CrewAI 抽象层级最高，代码量最少 |

### 5.3 推荐选择：自研轻量 Harness（参考 Claude Code 开源架构）

#### 推荐理由

**1. "框架提供便利，但也划定边界"——Agent 控制力是不可妥协的差异化能力**

AgentHub 的核心价值不是"能调用 Agent"，而是"如何精确地治理 Agent 的行为"。以下是 LangGraph/CrewAI 框架无法满足的 AgentHub 关键需求：

- **四级上下文压缩**：AgentHub 需要根据上下文窗口使用率自动在四种压缩策略之间切换——零 API 调用的 Snip 裁剪（节省成本）、只丢弃特定工具结果的 Micro 压缩（保留对话连贯性）、结构化投影的 Collapse（不修改原始消息）、LLM 摘要的 Auto（最终手段）。LangGraph 的 `trim_messages` 只提供了其中的 1/4 能力。
- **Token Budget 熔断**：AgentHub 需要实时追踪每次 LLM API 调用的 token 消耗，在剩余预算不足 5% 时强制收束返回 partial result。这不是框架层面的功能，而是需要在每次 API 调用前后插入精确的 token 计数逻辑。
- **Tool Registry 的 Fail-Closed 模型**：AgentHub 要求所有工具（包括 MCP Server 动态发现的工具）默认不可用，只有显式注册且通过权限检查后才能调用。框架提供的工具注册机制通常是 Fail-Open（注册即可用），与 AgentHub 的安全模型相反。

这些需求如果在 LangGraph 或 CrewAI 上实现，需要大量的 monkey-patch 和 hack，最终得到的仍是一个"披着框架外衣的自研方案"——代码与框架深度耦合，升级框架版本可能破坏自定义逻辑。

**2. Claude Code 开源架构提供了"学习成本"的最优解**

自研 Harness 最大的担忧是"从零开始"，但 Claude Code 的开源架构（Agent Loop 的 AsyncGenerator 模式、Tool Registry 的 buildTool 工厂模式、四级压缩管道、Token Budget 熔断）为 AgentHub 提供了可直接参考的架构蓝图：

- **不是从零发明，而是适配重构**——将 Claude Code 的通用 Agent 架构适配为 AgentHub 的多 Agent 协作场景
- **AsyncGenerator 模式是 TypeScript 的标准特性**，不依赖任何第三方库
- **设计模式（工厂模式、状态机、管道模式）** 是成熟的软件工程实践，非 Claude Code 独有

**3. 比赛评审的加分项**

自研 Harness 在比赛中展示的是"对 Agent 运行时的深度理解"，而非"会调用框架 API"。在技术评审中，展示以下内容远比"我们用 LangGraph"有说服力：

- AsyncGenerator 驱动的 16 步 Agent Loop 设计（为什么是 16 步、每步的职责边界）
- 四级压缩管道的触发阈值调优（snip 边界设多少条消息、collapse 的摘要粒度）
- Token Budget 的黄区/红区/熔断区设置依据（预算分配公式）

### 5.4 放弃方案的理由

- **LangGraph**：是一个优秀的框架，适合需要 Human-in-the-Loop 审批、多分支路由、Checkpoint 回放的企业级工作流。但 AgentHub 的需求恰好在框架的"边界之外"——我们需要的是"LLM 调用的底层控制"而非"工作流图的高层编排"。如果选择 LangGraph 但又在框架之上大量 hack，反而失去了使用框架的意义。
- **CrewAI**：定位是"角色化多 Agent 快速原型"，与 AgentHub 的阶段定位似乎契合，但其抽象层级太高导致控制力严重不足。CrewAI 的 Agent、Task、Crew、Process 概念是它自己的抽象体系，无法映射到 AgentHub 的 Orchestrator → Harness → Adapter 三层架构。强行使用会导致架构层级的崩塌和概念混乱。

## 6. 沙箱方案对比选型

### 6.1 候选方案

| 方案 | 核心特征 |
|------|----------|
| **A: iframe + srcdoc**（类似 CodePen） | 纯前端沙箱、零服务端依赖、浏览器原生安全隔离（同源策略）、postMessage 通信 |
| **B: WebContainer**（StackBlitz 技术） | 浏览器内 Node.js 运行时、完整文件系统、npm 包安装、开发服务器 |
| **C: Docker 容器沙箱** | 完整 Linux 环境、任意编程语言、cgroups 资源限制、seccomp 安全策略 |

### 6.2 多维度评估

| 评估维度 | A: iframe + srcdoc | B: WebContainer | C: Docker 容器沙箱 |
|----------|-------------------|-----------------|---------------------|
| **预览静态页面的能力** | 🟢 完美 — 原生渲染 HTML/CSS/JS，支持所有浏览器 API（DOM、Canvas、WebGL、Service Worker），CSS Grid/Flexbox 无限制 | 🟢 完美 — 同样基于浏览器渲染，但额外可以运行 dev server 实现模块热更新 | 🟢 可 — 通过暴露 HTTP 端口 + iframe 嵌入，但需要网络映射和端口管理 |
| **安全隔离级别** | 🟢 高 — 浏览器同源策略天然隔离，iframe sandbox 属性可限制 `allow-scripts` / `allow-forms` / `allow-popups`；`srcdoc` 不产生网络请求，内容完全受控 | 🟡 中 — WebContainer 运行在浏览器内，但执行 Node.js 代码，需依赖 StackBlitz 的安全沙箱实现 | 🟢 极高 — 完整 Linux namespace 隔离 + cgroups 资源限制 + seccomp 系统调用过滤 + AppArmor/SELinux |
| **HMR 热更新** | 🟡 中 — 需前端自行实现：监听代码变更（WebSocket/SSE）→ 更新 iframe srcdoc 属性 → iframe 重新渲染（非增量，是整体刷新）；实现增量 HMR 复杂度高 | 🟢 优 — WebContainer 内置 Vite/dev server，天然支持模块级 HMR，无需额外开发 | 🟡 中 — 可通过 WebSocket 推送 → 文件替换 → dev server HMR 实现，但链路长（服务端→WS→iframe→dev server） |
| **实现复杂度** | 🟢 极低 — ~50 行代码即可实现基础预览：`<iframe srcdoc={htmlContent} sandbox="allow-scripts" />` + postMessage 通信 | 🟡 中 — 需要引入 `@webcontainer/api`，理解其文件系统和进程模型，初始化流程约 100-200 行 | 🔴 高 — 需要容器管理（创建/销毁/资源限制/端口映射）、镜像管理、安全策略配置、日志收集 |
| **比赛资源约束** | 🟢 无约束 — 纯浏览器端执行，不消耗服务端资源，不影响比赛 Demo 的单节点部署 | 🟡 中 — 消耗用户浏览器内存（~200MB+），低配设备可能卡顿 | 🔴 高 — 需要服务端 Docker daemon 运行，每个沙箱 ~50-200MB 内存，并发 10 个沙箱消耗 1-2GB 服务端内存 |

### 6.3 推荐选择：Sandpack（CodeSandbox 开源），架构预留 WebContainer 接口

#### 推荐理由

**1. Sandpack — 比自研 iframe 更好的开箱即用方案**

经过开源项目调研（详见 [开源项目参考与复用分析](./开源项目参考与复用分析.md#6-网页预览沙箱)），发现 **Sandpack**（CodeSandbox 开源）在一个 npm 包中覆盖了我们原本需要自研的所有预览功能：

| 能力 | 自研 iframe | **Sandpack** |
|------|------------|-------------|
| 多文件项目 | 需自己组装 HTML | ✅ 内置模板系统（React/Vue/Vanilla） |
| HMR 热更新 | 需自己实现 | ✅ 开箱即用 |
| 安全隔离 | 手动配置 sandbox | ✅ 内置沙箱 |
| TypeScript 编译 | ❌ 无法编译 | ✅ 浏览器内编译 |
| npm 依赖 | ❌ 不支持 | ✅ 支持 npm 包安装 |
| 视口切换 | 需自己实现 | ✅ 内置 Responsive |
| 代码量 | ~200 行 | **~20 行** |

仅需 20 行代码集成：
```tsx
import { Sandpack } from '@codesandbox/sandpack-react'
<Sandpack template="react" files={agentGeneratedCode} />
```

**1. MVP 阶段的"够用"原则**

AgentHub 的 MVP 场景是 Agent 生成前端代码（HTML/CSS/JS）→ 用户在 IM 对话中预览效果。iframe + srcdoc 完美覆盖这一场景：

- Agent 生成的代码通过 WebSocket 推送到前端
- 前端组装完整 HTML 文档
- 设置 `<iframe>` 的 `srcdoc` 属性，浏览器立即渲染
- 通过 `postMessage` 实现预览面板与主应用的通信（如切换视口尺寸）

这个流程对比赛 Demo 来说完全足够——它展示的是 AgentHub 的核心价值（Agent 生成可预览的代码），而非预览技术的复杂度。

**2. iframe sandbox 的安全模型与 AgentHub 的安全理念一致**

```html
<iframe
  srcdoc={htmlContent}
  sandbox="allow-scripts allow-forms"
  // 不包含 allow-same-origin（防止访问父页面 DOM）
  // 不包含 allow-top-navigation（防止劫持页面导航）
  // 不包含 allow-popups（防止弹窗骚扰）
/>
```

`srcdoc` 属性（而非 `src` URL）确保内容完全来自 AgentHub 前端，不会产生额外的网络请求。`sandbox` 的默认值是"全部禁止"，需要显式开放权限——这与 Harness 层 Tool Registry 的 Fail-Closed 安全模型一脉相承。

**3. 架构预留 WebContainer 接口的渐进策略**

虽然 MVP 阶段不需要 WebContainer，但在架构设计上预留接口：

```typescript
interface IPreviewSandbox {
  // MVP: iframe + srcdoc
  render(html: string, options?: RenderOptions): void;
  
  // Phase 2: WebContainer
  mountProject(files: FileMap): Promise<void>;
  startDevServer(): Promise<{ url: string }>;
  onHMR(callback: (update: HMRUpdate) => void): void;
  
  // Phase 3: Docker
  deployToContainer(image: string, config: ContainerConfig): Promise<ContainerHandle>;
}
```

这确保了在 Phase 2 引入 WebContainer（支持 npm 依赖、模块热更新）时，上层调用方无需改动。

### 6.4 放弃方案的理由

- **WebContainer（MVP 阶段）**：对于比赛 Demo 来说"杀鸡用牛刀"。AgentHub 的首个 Demo 场景是静态网页预览（Agent 生成一个 Todo App 的 HTML/CSS/JS），iframe + srcdoc 在 50 行代码内解决，而 WebContainer 需要引入额外 SDK、理解文件系统和进程模型。当 Demo 演进到需要 npm 依赖（React/Vue 项目）时，再切换到 WebContainer——此时架构已预留接口，切换成本低。
- **Docker 容器沙箱**：比赛阶段运维成本不可接受。需要管理 Docker daemon、镜像拉取、容器生命周期、端口映射、资源清理。10 个并发 Agent 各需一个沙箱，服务端内存消耗巨大。适合 Phase 3 的多租户生产环境，不适合 MVP。

## 7. 实时通信方案

### 7.1 候选方案

| 方案 | 核心特征 |
|------|----------|
| **A: 原生 WebSocket（Bun 内置）** | 全双工双向通信、~50μs 服务端 RTT、Bun `Bun.serve()` 原生支持、零额外依赖 |
| **B: SSE（Server-Sent Events）** | 服务端→客户端单向推送、基于 HTTP 协议、浏览器原生 `EventSource` API、自动重连 |
| **C: Socket.io** | WebSocket 上层封装、自动降级（WS→长轮询）、房间/命名空间、内置重连和心跳 |

### 7.2 多维度评估

| 评估维度 | A: 原生 WebSocket | B: SSE | C: Socket.io |
|----------|-------------------|--------|--------------|
| **IM 聊天实时性** | 🟢 极优 — 用户发送消息 → WebSocket 推送 → Agent 回复 → WebSocket 推送，全链路 < 50μs（不含 Agent 思考时间） | 🔴 不适用 — SSE 是单向（服务端→客户端），用户发送消息仍需 HTTP POST，无法实现真正的双向 IM | 🟢 极优 — 同原生 WebSocket 性能（底层也是 WS），额外有房间管理便利 |
| **流式 Agent 消息推送** | 🟢 优 — 服务端每次 `yield` 新文本块 → `ws.send(delta)` → 客户端逐块渲染，但需要自定义流结束标记 | 🟢 极优 — SSE 设计初衷就是"服务端推送事件流"，Agent 的 token 级输出是 SSE 的完美使用场景：`data: {"delta": "你好"}\n\n` → `data: {"delta": "，我来"}\n\n` → ... → `data: [DONE]` | 🟢 优 — 同 WebSocket，额外有 `socket.emit('stream:delta', chunk)` 的语义化事件名 |
| **Bun 原生 WebSocket 性能** | 🟢 极优 — `Bun.serve()` WebSocket 单机 10 万+ 并发连接，每连接内存 ~4KB；ping/pong 内置（`ws.ping()` / `ws.pong()`），无需手动实现心跳 | 🔴 差 — SSE 需要 Bun HTTP 服务器长连接支持，但 Bun 对 SSE 无特殊优化（本质是 HTTP 长连接） | 🟡 中 — Socket.io 在 Bun 上运行需要适配层（`bun-socket.io`），失去部分性能优势 |
| **协议复杂度** | 🟡 中 — 需要自定义消息协议（JSON 序列化/反序列化、消息类型路由、心跳机制、断线重连逻辑） | 🟢 低 — 标准 HTTP 协议，浏览器 `EventSource` 自动处理重连和 `Last-Event-ID` | 🟢 低 — Socket.io 封装了所有底层细节，开箱即用 |

### 7.3 推荐选择：原生 WebSocket（Bun 内置）用于核心 IM，SSE 用于流式回复推送

#### 推荐理由

**1. 双通道架构：WebSocket 做双向 IM，SSE 做单向流式推送**

AgentHub 的通信模式天然是混合的：

| 场景 | 通信方向 | 最佳协议 | 理由 |
|------|----------|----------|------|
| 用户发送消息 | 客户端 → 服务端 | HTTP POST 或 WebSocket | 需要携带完整消息体（文本+附件+@指令），WebSocket 天然支持 |
| IM 消息实时推送 | 服务端 → 客户端 | WebSocket | 需要低延迟（< 50ms）、双向确认（已送达/已读回执）、多会话复用同一条连接 |
| Agent 流式回复 | 服务端 → 客户端 | **SSE** | 逐 token 推送，客户端只需消费不需发送；SSE 的 `EventSource` API 比 WebSocket 更适合"流"的语义；浏览器原生 `EventSource` 自动处理重连 |
| 部署状态推送 | 服务端 → 客户端 | WebSocket | 需要和 IM 消息复用同一连接以减少连接数 |
| Diff 结果推送 | 服务端 → 客户端 | WebSocket | 同上，复用连接 |

实际的协议分配：

```
WebSocket（持久连接，心跳 30s）:
├── chat.message（用户消息 客户端→服务端）
├── chat.message（Agent 非流式回复 服务端→客户端）
├── tool.use / tool.result（工具调用可视化）
├── diff.generated（Diff 结果推送）
├── deploy.status / deploy.log（部署进度）
├── system.heartbeat / system.heartbeat.ack
└── system.error

SSE（按需建立，流结束自动关闭）:
└── chat.stream.delta（Agent 流式文本块，逐 token 推送）
```

**2. 为什么不是纯 WebSocket 做所有事？**

Agent 的流式回复用 SSE 而不是 WebSocket，原因有三：

- **语义清晰**：SSE 的 `EventSource` 就是为"事件流"设计的——`event: delta` + `data: chunk` + 结束标记 `[DONE]`。WebSocket 用于流式响应则需要自定义"流开始"和"流结束"消息类型，消息协议更复杂。
- **资源隔离**：每个 SSE 连接对应一个流式响应，响应结束自动关闭连接。WebSocket 连接是持久化的，如果流式响应和 IM 消息复用同一条连接，消息类型路由逻辑会更复杂。
- **浏览器兼容**：`EventSource` API 在所有现代浏览器中原生支持，不需要引入任何 polyfill。

**3. 为什么不是 Socket.io？**

Socket.io 的价值在于：
- 自动降级：WebSocket 不可用时回退到 HTTP 长轮询
- 房间/命名空间：简化群聊消息广播
- 内置重连和心跳

但 AgentHub 的场景下这些价值都打了折扣：
- 2026 年的浏览器 WebSocket 支持率 > 98%，6 年前需要担心的降级场景几乎不存在
- Bun 的 `Bun.serve()` 原生 WebSocket 已经内置了 ping/pong 心跳，不需要 Socket.io 的心跳机制
- Socket.io 引入了一个额外的依赖链（socket.io + socket.io-client），且在 Bun 运行时中需要额外适配——为"可能用不到"的降级能力增加依赖违背"最小依赖"原则

### 7.4 放弃方案的理由

- **纯 SSE 方案**：无法实现双向 IM（用户发送消息仍需 HTTP POST），两条通信路径（POST + SSE）增加了状态同步的复杂度。
- **Socket.io**：在 2026 年 WebSocket 普及率下，Socket.io 的"自动降级"价值有限，引入额外依赖和 Bun 适配成本，不符合"最小依赖"原则。
