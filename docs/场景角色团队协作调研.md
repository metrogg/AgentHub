# 场景、角色与团队协作调研

最后更新：2026-06-01

这份文档回答一个问题：AgentHub 不能只靠一套默认角色跑所有任务。不同场景需要不同的团队拓扑、协作节奏和产物链。角色库可以保留，但只能作为能力画像和创建参考，不能再次变成固定团队模板。

## 结论先行

1. 场景决定协作逻辑，不是角色名决定协作逻辑。
2. 角色是能力画像，不是默认编排结果。
3. 团队是运行时临时组装的，可能是 1 人、3 人、5 人，也可能是并行小组。
4. Orchestrator 的职责是根据目标、约束、产物和风险动态组队，而不是把所有任务都套进 Researcher / Builder / Reviewer 三段式。
5. MCP、Skills、Rules 属于能力层；A2A 属于通信层；AG-UI 属于运行呈现层。

## 为什么默认角色不够

当前常见默认角色只有：

- Orchestrator
- Clarifier
- Architect
- Researcher
- Coder
- Verifier
- Reviewer
- Integrator
- Custom

这组角色足以覆盖“通用软件开发”里的大部分任务，但一旦进入别的场景，就会出现两个问题：

- 角色语义不够细，无法表达关键能力差异。
- 团队拓扑不够灵活，无法表达不同协作节奏。

例如：

- 调研写作任务，更需要 Research + Synthesis + Fact Check。
- 设计任务，更需要 Product + UX + Copy + Visual。
- 交付任务，更需要 Plan + Build + Validate + Release。
- 长链路任务，更需要 Handoff + Checkpoint + Resume + Exception handling。

## 场景分类

### 1. 软件开发类

典型目标：

- 做网站
- 改前端页面
- 接接口
- 修 bug
- 重构模块
- 写测试

更适合的协作逻辑：

- 先澄清范围，再动态拆 DAG。
- 研究、实现、审查、验证可并行或串行混合。
- 产物链最重要的是 diff、测试结果、预览、风险说明。

更适合的角色组合：

- Orchestrator
- Architect
- Coder
- Reviewer
- Verifier
- Integrator

### 2. 调研分析类

典型目标：

- 行业调研
- 竞品对比
- 技术选型
- 数据归纳
- 输出报告或 PDF

更适合的协作逻辑：

- Researcher 并行采集。
- 需要事实校验和冲突消解。
- 最终必须有 Synthesizer / Writer 统一成文。

更适合的角色组合：

- Orchestrator
- Researcher
- Fact Checker / Verifier
- Synthesizer / Writer
- Reviewer

### 3. 设计创意类

典型目标：

- 页面结构
- 视觉方案
- 文案
- 品牌调性
- 交互草图

更适合的协作逻辑：

- 设计先于实现。
- 需要多方案并行比较，而不是单一路径执行。
- 产物重点是草图、设计说明、文案候选、页面结构。

更适合的角色组合：

- Orchestrator
- Product Designer
- UX Writer
- Visual Designer
- Reviewer

### 4. 内容生产类

典型目标：

- 文章
- 演讲稿
- 汇报材料
- PRD
- README

更适合的协作逻辑：

- 先提纲，再分段写，再总编统一语气和结构。
- 需要多轮修订和一致性检查。

更适合的角色组合：

- Orchestrator
- Outliner
- Writer
- Editor
- Reviewer

### 5. 运营 / 发布 / 自动化类

典型目标：

- 部署
- 发布静态站点
- 批处理数据
- 自动化脚本
- 连接外部系统

更适合的协作逻辑：

- 安全优先。
- 审批点要前置。
- 需要清晰的变更记录和回滚策略。

更适合的角色组合：

- Orchestrator
- Builder
- Verifier
- Release / Operator
- Reviewer

### 6. 长周期协作类

典型目标：

- 大型产品开发
- 多阶段交付
- 需要暂停、恢复、补充信息
- 跨多个会话接力

更适合的协作逻辑：

- 任务必须有 checkpoint。
- 子对话和产物必须可追踪。
- Orchestrator 要能重新规划，而不是只等最终结果。

更适合的角色组合：

- Orchestrator
- Planner
- Specialist sub-agents
- Synthesizer
- Integrator

## 团队拓扑，而不是固定团队

AgentHub 未来更应该支持这些拓扑，而不是固定角色名单：

| 拓扑 | 适合场景 | 特点 |
| --- | --- | --- |
| 单执行体 | 简单问答、小修小改 | 成本最低，最快 |
| 主从式 | 大多数编码任务 | Orchestrator 统一调度子 Agent |
| 并行采集式 | 调研、竞品、资料整理 | 多个 Agent 并行收集，再汇总 |
| 串行流水线式 | 设计 -> 实现 -> 测试 -> 发布 | 每一步产物进入下一步 |
| 审查闭环式 | 高风险修改、上线前验收 | Build 与 Review 分离 |
| 分组协作式 | 大任务、多模块 | 不同小组负责不同子域 |
| 事件驱动式 | 长周期任务、频繁中断 | 状态和事件比一次性回复更重要 |

## 对 AgentHub 的建议

### 1. 角色库改成能力库

角色不再表示“默认团队成员”，而是表示：

- 能做什么
- 适合什么任务类型
- 需要什么工具
- 产出什么制品
- 风险等级如何

### 2. 团队由 Orchestrator 动态组装

Orchestrator 看到目标后，应该输出：

- 需要哪些角色
- 每个角色的职责
- 哪些任务并行
- 哪些任务依赖前置结果
- 哪些任务需要用户确认

### 3. 场景只做“推荐模型”，不做“固定模板”

可以有场景推荐，但只能是：

- 给 Orchestrator 的建议
- 给用户的参考
- 给角色创建时的提示

不能是：

- 自动注入固定团队
- 自动写死 Researcher / QA / Builder 流程
- 关键词命中就直接分派

### 4. 增加“场景画像”而不是“场景模板”

建议未来增加一个轻量场景画像层，例如：

- 开发类
- 研究类
- 设计类
- 内容类
- 运维类
- 长周期类

画像只提供：

- 推荐角色
- 推荐拓扑
- 推荐产物
- 推荐风险点

不直接变成执行模板。

## 对现有默认角色的补充方向

现有角色可以继续保留，但建议增加这些能力语义：

- Product Manager：澄清目标、定义验收
- Analyst：数据分析、信息归纳
- Writer / Editor：内容生产与润色
- Tester / Verifier：验证与回归
- Release / Operator：发布和部署
- Security Reviewer：安全审查
- Integrator：集成和冲突消解

这些都应该是“可选扩展角色”，不是默认模板。
