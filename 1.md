  ---
  三、关键问题诊断

  1. 架构文档与代码严重脱节

  ARCHITECTURE.md 和 PRD.md 基于 Python FastAPI + PostgreSQL + Redis 设计，而实际代码是 Bun + Hono + SQLite。这会导致：
  - 后续开发者被文档误导
  - 很多设计（如 Redis Pub/Sub、Alembic 迁移、Docker 沙箱）在当前栈中需要重新设计

  2. 前端功能几乎为 0

  - LoginPage.tsx：纯 UI，无表单校验、无 API 调用
  - ChatPage.tsx：只有标题和提示文字
  - ChatContainer.tsx / AgentCard.tsx / TaskTree.tsx / DiffViewer.tsx：全部是"待实现"空壳
  - useWebSocket.ts：只建立连接，无消息监听、无重连、无心跳
  - authStore.ts：有状态定义，但无登录/注册 action

  3. 后端缺少"Agent"灵魂

  - agents.ts 路由：只有列表/详情查询，无调用接口
  - messages.ts 路由：只存用户消息，不触发任何 Agent 回复
  - tasks.ts 路由：只读，无创建/执行/状态流转
  - WebSocket：不处理任何业务消息

  五、立即可开始的 3 个具体任务

  如果你决定马上推进，建议按以下顺序：

  1. 打通前端登录流程
    - LoginPage.tsx 添加表单状态、调用 api.auth.login.$post()、写入 authStore
    - authStore 添加 login() / register() action，页面刷新时从 localStorage 恢复 token
  2. 实现 WebSocket 消息广播
    - 后端 index.ts 的 websocket.message 中解析 JSON，按 sessionId 广播到同一房间的所有连接
    - 前端 useWebSocket.ts 添加 onMessage 回调注册机制
  3. 实现最简单的 Agent 回复
    - 后端在收到用户消息后，调用 Anthropic API，将流式响应通过 WebSocket 推回前端
    - 前端在 ChatContainer 中展示流式文本（类似打字机效果）

  ---
  六、关于技术栈的决策建议

  当前代码使用 Bun + Hono + SQLite 是合理且务实的：
  - 零 Docker 依赖，比赛/演示环境友好
  - 全 TypeScript，前后端共享 Zod schema
  - SQLite 对于单租户 Demo 完全足够

  不建议再切回 Python FastAPI + PostgreSQL，成本太高。如果确实需要 Redis（WebSocket 多实例广播、分布式锁），可以后续以可选依赖方式接入。

● 以上是我对 AgentHub 项目的完整调研分析。总结一下核心结论：

  现状：代码是一个"IM 聊天应用的空壳"，距离"多 Agent 协作平台"还有大量工作。最紧迫的问题是前端功能缺失 + Agent 调用逻辑完全空白。
建议路线：不要按旧文档的庞大蓝图一次性推进，而是分阶段——先让"用户发消息 → Agent 流式回复"这条黄金路径跑通，再叠加多 Agent、MCP、审批门等高级能力。
